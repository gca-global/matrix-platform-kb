# ADR-038: ITSM is ES256-only (SSO bearer + MCP issuer)

**Status**: Accepted  
**Date**: 2026-08-17  
**Supersedes**: [ADR-032](ADR-032.md) *only* for the MCP access-token signing algorithm (HMAC → ES256). The chat-agent / OAuth 2.1 + PKCE + delegation design in ADR-032 still stands.  
**Extends**: [ADR-011](ADR-011.md) (ES256 SSO signing), [ADR-018](ADR-018.md) / [ADR-027](ADR-027.md) (Third-Party Auth for own-DB apps)  
**Scope**: ITSM app `gca-global/matrix-itsm` (app DB `irjrcskfcyierdbefrpk`, SSO client `n~~I~WvqoL3FuQ_nj~G6LClHKED1HsDK`)

## Context

ITSM's app DB has been on Supabase Third-Party Auth against the SSO JWKS since 2026-06-09 (`tpa_status: provisioned`, `jwt_secret_name: null`). SSO therefore mints **ES256** for this client. PostgREST rejects any other algorithm with `401 PGRST301`.

Two HS256 remnants still caused My Queue / sidebar badge 401 storms:

1. **Shared `matrix_sso_access_token` on `intranet.sharpsir.group`** — sibling apps that still mint HS256 (e.g. Meeting Hub) overwrite the same localStorage key. ITSM then sent a still-valid-by-`exp` HS256 bearer to its ES256-only PostgREST while SSO refresh/`oauth-userinfo` continued to succeed (HS256 fallback).
2. **MCP access tokens** signed HS256 via `app_settings.mcp.jwt_secret` (ADR-032). MCP is pre-production, so a hard cutover is acceptable.

## Decision

### D1 — SSO user auth: ES256 only at PostgREST

- App DB and SSO/CDL clients use `postgrestAccessToken()`, which rejects any bearer whose JWT header `alg !== 'ES256'`, force-rotates once (bounded by the existing refresh backoff), then fails closed.
- `handleAuthError` force-rotates via `forceRefreshAccessToken()` and requires ES256 before success (does not treat `oauth-userinfo` success alone as recovery).
- Native GoTrue token `matrix_supabase_access_token` is never preferred for PostgREST.
- Sidebar / ticket poll hooks throw on PostgREST errors so React Query can recover; poisoned `ITSM_QUERY_CACHE` is cleared on auth recovery and logout.

### D2 — MCP issuer: ES256 (P-256) JWK pair

- `app_settings.mcp.jwt_secret` stores `{ alg: 'ES256', kid, privateJwk, publicJwk, version }` (key name unchanged so RLS exclusion lists keep working).
- `mcp-oauth` signs / `mcp-server` verifies ES256 only — no HS256 fallback; header `alg` must be `ES256` before verify (alg-confusion guard).
- `mcp-admin` rotate generates a P-256 keypair; Settings → MCP shows `kid` + alg.
- Migration `20260817081513_mcp_es256_rekey` clears the legacy hex secret and outstanding MCP tokens/grants. Admin regenerates the key from Settings after deploy.

### D3 — Out of scope

- Platform-wide HS256 **verify fallback** in shared SSO Edge Functions (`matrix-platform-foundation`) — KB hardening item H1; affects every app.
- Per-app localStorage key namespacing for `matrix_sso_*` (cross-app collision root cause) — platform follow-up; ITSM's alg guard is the local mitigation.
- Meeting Hub (and other remaining `jwt_secret_name` apps) migrating to TPA/ES256.

## Consequences

- Every JWT ITSM issues or accepts for user auth and MCP access is **ES256**.
- Sibling HS256 apps on the same intranet origin can still briefly poison shared storage; ITSM rotates or re-logins instead of flooding 401s.
- MCP agents must re-authorize after the rekey.
- KB `security-model.md` hybrid table no longer lists ITSM under "has `jwt_secret_name`".
