# ADR-032: Chat-identity binding + delegated minting for the ITSM MCP (HumaticAI agent)

**Status**: Accepted (revised 2026-06-17 — agent auth moved to OAuth client-credentials via `private_key_jwt`; interactive PKCE user-login removed)
**Date**: 2026-06-16
**Extends**: [ADR-011](ADR-011.md) (ES256 SSO signing), [ADR-012](ADR-012.md) (SSO as the sole identity authority; identity boundary), [ADR-019](ADR-019.md) (server-managed PKCE / bounded replay), [ADR-027](ADR-027.md) (Third-Party Auth for own-DB apps)
**Scope**: SSO project `xgubaguglsnokjyudgvc` (new `sso_delegation_grants` table, `mcp_resolve_user` RPC, `mint-delegated-token` EF) + ITSM app `itsm-2-1` (app DB `irjrcskfcyierdbefrpk`: `mcp_chat_links` / `mcp_link_requests` / `mcp_action_consents` / `mcp_client_assertions`; `mcp_oauth_clients` extended with `public_jwk`/`is_agent`; `mcp-server` / `mcp-oauth` / `mcp-admin` EFs; `/mcp/link` page).

> **2026-06-17 revision.** Agents no longer present the signing key as a bearer, and the interactive PKCE user-login flow (authorization code / refresh tokens / dynamic client registration / `/oauth/consent`) is **removed**. Every agent now authenticates the same way — **OAuth client-credentials using a `private_key_jwt` client assertion** (RFC 7521/7523), each agent its own client with its own registered public key. The signing key (`app_settings.mcp.jwt_secret`) becomes **server-only**: it signs issued MCP access tokens and is never a bearer. Per-user authority for advanced tools is unchanged (delegated minting / OBO, below).

## Context

The new requirement: the **HumaticAI** agent (an LLM over Telegram / WhatsApp /
Microsoft Teams) must call the MCP as a tool **on behalf of chat users**, while
holding **no SSO tokens and no per-user credentials**. The agent knows only the
chat platform and the platform's permanent user id. We must:

1. Bind a messenger account to a Matrix (SSO) identity **once**.
2. Thereafter let the agent act for that user **without** it ever holding a
   credential, with Postgres **RLS** enforcing access as the real user.
3. Keep SSO the **sole identity authority** (ADR-012) — no duplicated identity
   custody, no stored refresh tokens.

A rejected earlier design stored encrypted SSO refresh tokens in the ITSM DB.
That duplicates identity custody and creates a high-value token vault — exactly
what ADR-012 forbids.

## Decision

### 1. Delegated minting (no stored user credentials)

The SSO project gains a **`mint-delegated-token`** edge function. On each MCP
request for a linked chat user, the MCP asks SSO to mint a **short-lived
(~30 min) ES256 JWT** for that user against a **revocable delegation grant**.
The MCP caches the token **in memory for its lifetime only** and runs tools
through a **per-user RLS-bound PostgREST client** (Supabase Third-Party Auth,
ADR-027). No token is persisted anywhere; access ends when the grant is revoked
or expires.

The minted JWT carries the user's **real** scope/crud/tenant claims (same shape
`oauth-token` / `switch-role` emit) so RLS returns correct data. Least privilege
is enforced at two **other** layers: the agent is limited to a reduced **tool
surface** (tickets r/w, approvals act, KB read, profile), and sensitive/write
actions require **step-up consent** (below).

`sso_delegation_grants` columns: `user_id`, `client_id` (the ITSM-MCP delegate),
`platform`, `external_user_ref` (chat id, audit/dedup), `assurance`, `status`,
`created_at`, `revoked_at`, `last_minted_at`, `mint_count`. Service-role only.

### 2. Agent authentication = OAuth client-credentials via `private_key_jwt`

Every agent authenticates the **same way** — the method is shared, the key is
per-agent:

- **Each agent is its own OAuth client** (`mcp_oauth_clients` row, `is_agent=true`)
  with its own **registered public key** (`public_jwk`). The agent signs a
  short-lived JWT **client assertion** (`iss=sub=client_id`, `aud=token endpoint`,
  `exp` ≤ 5 min, unique `jti`) with its private key and POSTs it to
  `mcp-oauth/token` with `grant_type=client_credentials` and
  `client_assertion_type=…jwt-bearer`. The AS verifies the signature against the
  registered public key, enforces **one-time `jti`** replay protection
  (`mcp_client_assertions`), and issues a **1h MCP access token** (HS256, no
  refresh). No shared secret is ever transmitted; revocation and audit attribution
  are **per-agent**.
- **Signing key is server-only.** `app_settings.mcp.jwt_secret` signs/verifies the
  issued MCP access tokens and is **never** a bearer or shared with agents. A leaked
  signing key can no longer be replayed as an agent credential. (Managed from
  Settings → MCP → Configuration; masked in the UI.)
- **Identity is asserted via request headers** (`X-Chat-Platform`, `X-Chat-Scope`,
  `X-Chat-User-Id`, `X-Chat-Aad-Oid` for Teams), never via LLM-controllable tool
  arguments. The headers select the end user; the access token authenticates the
  agent.
- **MCP → SSO service credential** (`MCP → mint-delegated-token`): an SSO-side
  shared secret (`MCP_DELEGATION_SECRET`) in the ITSM EF environment, checked by
  the mint EF via the `X-Delegation-Secret` header.

This is a three-plane separation: inbound agent auth (`private_key_jwt`), access
control (basic/advanced tiering + per-request validation + revocation), and
outbound per-user auth (delegated mint). The credential reaching the agent is
never the credential reaching the data.

### 2a. Basic vs advanced tool tiering

Tools split by whether they need a verified 1:1 identity:

- **Basic** (`whoami`, `search_kb`, `get_article`, `create_ticket`): require
  **only** a valid agent access token (bearer). No per-user identity, no linkage,
  and they **never** trigger the SSO link/confirmation URL. They run under the service
  role with leak-safe queries (KB published-only; `create_ticket` is write-only
  and attributes the requester from args or a generic sentinel when unverified).
- **Advanced** (everything else — `get_ticket`, `list_tickets`, `update_ticket`,
  `search_assets`, `get_asset`, `list_pending_approvals`, `approve`, `reject`):
  require a verified **1:1** identity and a linked SSO account; they run under
  the minted per-user token + RLS.

**Identified** = `X-Chat-Scope` != `group` **AND** a usable chat user id on a
known platform. A **group** chat (or a direct chat with **no user id**) is
basic-only. When an advanced tool is called without identity, the MCP returns a
JSON-RPC `advanced_requires_dm` error (`-32003`) whose `data` carries
`cause` (`group_chat` | `no_user_id`), `tier`, `chat_scope`, `platform`,
`remediation: ask_user_to_dm`, `agent_guidance`, and `available_here` (the basic
tools still usable). The agent relays this in its own words, nudging the user to
re-send the request in a direct (1:1) message — no sensitive data is leaked. The
link/SSO-confirmation URL appears only in a 1:1 context once an advanced tool
needs linkage (`not_linked`).

### 3. Per-platform binding & assurance

- **Teams** → **auto-bind**, **high** assurance. `aadObjectId` = SSO `azure_oid`;
  the mint EF resolves the user via `mcp_resolve_user(azure_oid|email)` and
  creates the grant on first call. No interactive login.
- **Telegram / WhatsApp** → **one-time interactive SSO login** at `/mcp/link`,
  **interactive** assurance. The `link_account` tool returns a single-use URL;
  the user signs in (transparent if a session exists), and `mcp-oauth/link_complete`
  records the mapping + grant. Anchor on the **numeric/permanent** platform id
  (never `@handle`/phone).

### 4. Step-up consent

On linked agent sessions, `approve` / `reject` and ticket **close/resolve**
require a fresh **click-through** confirmation (defense-in-depth on any channel).
The tool returns `consent_required` + a `/mcp/link?step=…` URL; the user confirms
(SSO-authenticated, same identity), and the action is authorized for ~5 min,
single-use, keyed by chat identity + action + target. No token is handed back to
the agent.

### 5. Trust chain (must be authenticated end-to-end)

`Platform → (signed webhook) → HumaticAI → (private_key_jwt → MCP access token) →
MCP → (service cred) → SSO mint`. The chat id is **platform-asserted**, never user-asserted; HumaticAI
**must** verify the platform webhook signature (Telegram `X-Telegram-Bot-Api-Secret-Token`,
WhatsApp `X-Hub-Signature-256`, Teams Bot Framework JWT) before forwarding a chat
id. See `sso-edge-functions.md` and `api-contracts.md`.

## Consequences

- SSO remains the sole identity authority; **no user credentials** are stored in
  ITSM (only mappings + flow state). Grants are revocable per-user from
  Settings → MCP (revoke also revokes the SSO grant) and auto-expire after **90
  days of inactivity**.
- Blast radius of a leaked **agent private key** is bounded and **per-agent**:
  rotate or revoke that one agent (clear its `public_jwk` + revoke its tokens)
  without touching the signing key or any other agent. A leaked **signing key**
  can no longer be replayed as an agent credential (it is server-only and not a
  bearer). Advanced-tool exposure is further bounded by reduced tool surface,
  per-request short-lived per-user tokens, RLS, step-up consent, and audit. A
  leaked chat id alone grants nothing (the agent key + webhook verification are
  the linchpins).
- Residual risks: account compromise (SIM-swap/stolen session), WhatsApp number
  recycling, and the assurance downgrade of personal TG/WA vs corporate Teams.
  Mitigated by one-time strong binding, inactivity expiry, step-up for writes,
  `last_seen` visibility, and treating TG/WA as lower assurance.
- GDPR/consent: linking a messenger id to an employee identity is a deliberate,
  user-initiated, revocable act with clear consent copy on `/mcp/link`; the
  binding is the only personal datum stored and is admin-visible/erasable.

## Provisioning (one-time)

- Provision `MCP_DELEGATION_SECRET` on both the SSO `mint-delegated-token` EF and
  the ITSM EFs (`mcp-server`, `mcp-oauth`, `mcp-admin`).
- Register `/mcp/link` as a redirect URI on ITSM's SSO client.
- Ensure the MCP signing key is generated in Settings → MCP → Configuration
  (`app_settings.mcp.jwt_secret`) — server-only, never handed to an agent.
- Register each agent in Settings → MCP → Agents (upload its public-key JWK, or
  let the server generate a keypair and reveal the private key once). Give the
  agent its `client_id`, the token endpoint, and its private key (out-of-band).
