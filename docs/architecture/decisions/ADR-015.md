# ADR-015: CDL Pipeline EF Surface — broker-scope CRUD for Matrix Pipeline

**Status:** Proposed
**Date:** 2026-05-28
**Deciders:** platform team (CDL owners) + Pipeline team (matrix-pipeline / matrix-pipeline-2.0)
**Related:** ADR-008 (5-level scope), ADR-011 (ES256), ADR-012 (CDL Third-Party Auth), ADR-013 (matrix-platform-foundation owns CDL + SSO), ADR-014 (Unified MLS ingestion pipeline)
**Supersedes:** —
**Superseded by:** —

## Context

`matrix-pipeline` (the CRM, Lovable-managed Phase-1+ build) is the canonical RESO DD 2.0 consumer of CDL (`ofzcokolkeejgqfjaszq`). Its brokers operate under SSO scopes `self` / `team` / `global` (per [ADR-008](ADR-008.md)). A live audit of CDL on 2026-05-28 (see `mem://infrastructure/cdl-coverage.md` in the matrix-pipeline repo) revealed three structural facts that block the build:

1. **All 12 RESO resources flagged in the original prompt as `PGRST205` (404) are absent from the CDL `public` schema today**. The "PGRST205 means missing anon SELECT grant" hypothesis is rejected — anon `SELECT` is granted on every existing public table; the resources simply do not exist as tables.
2. **There is no `pipeline:*` EF family**. The only EF with `list-resource` / `upsert-resource` / `delete-resource` actions is `mls-sync` ([matrix-platform-foundation/supabase/cdl/functions/mls-sync/index.ts](https://github.com/sharpsir-group/matrix-platform-foundation/tree/main/supabase/cdl/functions/mls-sync)) — an Atlas-owned admin EF. The generic `cdl-write` EF listed for `matrix-pipeline` in [`docs/platform/api-contracts.md`](../../platform/api-contracts.md) is **not built**.
3. **`mls-sync` is NOT broker-callable**. It enforces `ALLOWED_SCOPES = system_admin,org_admin` (`index.ts` lines 67-128). Any broker-scope JWT (`self` / `team` / `global`) is rejected with 403. Even for the 10 RESO resource names `mls-sync` technically supports (`properties`, `members`, `offices`, `contacts`, `openHouses`, `showings`, `history`, `tracking`, `rooms`, `unit_types`), Pipeline cannot use it.

**Net consequence today**: Pipeline can READ a curated subset of CDL via SSO-JWT-on-PostgREST + the broker-scope-friendly `listings-search` EF (which is scoped to `self,team,global,org_admin,system_admin`), but it has **zero broker-scope WRITE surface into CDL**. Every Phase-1/2/3/4 write must happen in the CRM app DB.

Two additional drift items confirmed by the audit:

- `public.teams` was **DROPPED** 2026-05-04 in migration [20260504080000_pr1_5_pr1_6_drop_teams_and_power_production.sql](https://github.com/sharpsir-group/matrix-platform-foundation/tree/main/supabase/cdl/migrations) (PR1.5 rationale: 0 rows, 0.3% WgtOrg adoption, "Cyprus market does not operate as MLS teams"). [cdl-schema.md](../../data-models/cdl-schema.md) lines 280-283 + 376 still list `public.teams` and `v_dash_teams` as Phase-1 live. **KB doc is ~24 days stale.**
- `ShowingAppointment` naming drift: `cdl-schema.md` line 280 calls it `public.showing_appointments`; live is `public.showings`. Acknowledged in [`wiki/architecture.md` Naming drift advisory](../../product-specs/matrix-pipeline/wiki/architecture.md) but unfixed in the canonical schema doc.

## Decision

Bundle six platform-foundation deliverables into the next CDL release. Pipeline team drafts; platform team accepts/amends/sequences.

### #1 — KB schema-doc drift fix

Patch [`docs/data-models/cdl-schema.md`](../../data-models/cdl-schema.md):

- Drop `public.teams` and `v_dash_teams` from the Phase-1 expansion table (lines 280-283 + 376) — reflect the PR1.5 DROP.
- Rename `public.showing_appointments` → `public.showings` (line 280) — reflect the live table name.
- Add `public.contact_listings` (24 979 rows) and `public.contact_listing_notes` to the Phase-1 expansion table with their **RLS-disabled** status explicitly flagged.

Owner: KB maintainer (platform). Estimated effort: 30 min PR.

### #2 — EF pair: `cdl-contacts-read` + `cdl-contacts-write`

Broker-scope-callable EFs for the PII `public.contacts` table:

- `verify_jwt: false`; EF verifies SSO JWT itself.
- Allowed scopes: `self,team,global,org_admin,system_admin`.
- Tenant scoping enforced by the EF (`tenant_id` from JWT claims).
- PII redaction by role: brokers see only their `OwnerMemberKey` rows + team rows; PII fields gated by scope.
- `cdl-contacts-read`: list / get / filter by `owner_member_key`, `contact_type`, `lead_source`, etc.
- `cdl-contacts-write`: insert / update / soft-delete (`is_deleted = true`). On every write, the EF also inserts a corresponding `HistoryTransactional` row (`ResourceName = 'Contacts'`, `ResourceRecordKey = <ContactKey>`, `MajorChangeType = …`).

Owner: platform. Unblocks Phase-1 Pipeline Contacts.

### #3 — EF: `cdl-history-emit` (most critical)

A broker-scope-callable EF for inserting into `public.history_transactional`. Today RLS allows anon SELECT but writes are service-role only — so brokers cannot emit history events from the UI. This is a hard violation of the [Audit gate](../../product-specs/matrix-pipeline/wiki/architecture.md#compliance-gates) (compliance gate #3: every state transition MUST emit a `HistoryTransactional` row).

- `verify_jwt: false`; EF verifies SSO JWT.
- Allowed scopes: `self,team,global,org_admin,system_admin`.
- Append-only contract: refuses updates / deletes; insert only.
- Body shape: full canonical RESO `HistoryTransactional` record (`resource_name`, `resource_record_key`, `major_change_type`, `change_type`, `entity_event_sequence`, `change_timestamp`, `field_name`, `previous_column_value`, `new_column_value`, etc.).

Single most important EF in this ADR — without it, Pipeline cannot satisfy compliance gate #3 from broker UI.

### #4 — EF pair: `cdl-contact-listings-read` + `cdl-contact-listings-write` (+ RLS Pattern B)

`public.contact_listings` (24 979 rows) and `public.contact_listing_notes` are present in CDL but have **RLS DISABLED** — anyone with the anon key reads/writes all-broker, all-client engagement history. This is a CDL access gate violation flagged in [`wiki/architecture.md` Security advisory](../../product-specs/matrix-pipeline/wiki/architecture.md).

This ADR item delivers both halves:

- Two EFs (`-read`, `-write`) with broker scope + tenant scoping + per-broker filtering (a broker sees only their `Contacts` rows' junctions).
- RLS Pattern B (`security-model.md`) rollout on both tables: enable RLS, write tenant + scope policies, deny direct anon r/w.

Owner: platform. Closes the gate violation + unblocks Phase-3 ContactListings.

### #5 — Roster decision: Teams / TeamMembers / OUID

None of the three are in CDL today (Teams was actively DROPPED PR1.5). None are in SSO either (only `public.offices` and `public.role_configurations` exist in `xgubaguglsnokjyudgvc`). Pipeline needs a Team identity for the FR-CON / FR-FNL FR cluster.

Two options:

**Option A — Re-introduce `public.teams` + `public.team_members` + `public.ouid` in CDL** in the Phase-2+ migration, with `cdl-teams-{read,write}` and `cdl-team-members-{read,write}` EFs. Pure canonical-RESO compliance.

**Option B (Pipeline preference) — Derive Team identity from SSO groups** via a new `sso-teams-resolve` EF that proxies SSO groups into a Teams-shaped DTO (mapping `SSO group ↔ Teams.TeamKey` per [`wiki/architecture.md#identity-boundary`](../../product-specs/matrix-pipeline/wiki/architecture.md#identity-boundary)). Cypress market does not run MLS teams (PR1.5 rationale); the brokerage operates via SSO groups already. Cheaper to deliver, cheaper to maintain.

Platform team picks one. Pipeline favours **Option B** for the Phase-1-4 timeline.

### #6 — Roadmap commitment with ETAs for the Phase-2+ migration

For each of the 10 canonical RESO resources currently missing from CDL, platform commits an ETA + owner:

| Resource | Target table | Target EF pair |
|---|---|---|
| `SavedSearch` | `public.saved_search` | `cdl-saved-search-{read,write}` |
| `Prospecting` | `public.prospecting` | `cdl-prospecting-{read,write}` |
| `ShowingAvailability` | `public.showing_availability` | `cdl-showing-availability-{read,write}` |
| `ShowingRequest` | `public.showing_requests` | `cdl-showing-requests-{read,write}` |
| `Showing` (recorded fact, separate from Appointment) | `public.showings_recorded` | `cdl-showings-recorded-{read,write}` |
| `LockOrBox` | `public.lock_or_box` | `cdl-lock-or-box-{read,write}` |
| `Caravan`, `CaravanStop` | `public.caravans`, `public.caravan_stops` | `cdl-caravan-{read,write}`, `cdl-caravan-stop-{read,write}` |
| `TransactionManagement` | `public.transaction_management` | `cdl-tm-{read,write}` (Phase-4 hard blocker) |
| `OUID` | `public.ouid` (Option A only) | `cdl-ouid-{read,write}` |
| `TeamMembers` | `public.team_members` (Option A only) | `cdl-team-members-{read,write}` |

Each table follows the CDL canonical pattern (`id uuid pk`, RESO canonical PascalCase → snake_case columns, `raw jsonb`, `content_hash`, soft-delete, `locked_fields jsonb`, `source_id`). Each EF follows the [security-model.md](../../platform/security-model.md) verify-JWT contract.

`cdl-showings-write` is added here too (the existing `public.showings` table can already be read but is service-role-write-only — Pipeline needs a broker-scope writer for ShowingAppointment).

ETA owner: platform team.

## Consequences

**For Pipeline:**

- Phase-1 (Contacts) ships once #2 lands. Until then, `cdl-contacts-{read,write}` returns `501 EF_NOT_AVAILABLE`; Pipeline queues writes in `contacts_pending` and shows a "pending platform EF" banner.
- Phases 2-4 ship to the CRM app DB now with RESO snake_case columns (zero-rename mirror); the canonical CDL home opens when #6 lands.
- `HistoryTransactional` emissions queue in `history_pending` until #3 lands; a Phase-7 reconciler drains the queue once the EF ships. This satisfies compliance gate #3 (Audit gate) via eventual delivery rather than synchronous write.
- `public.contact_listings` + `public.contact_listing_notes` direct anon access is forbidden by the CDL access gate today; #4 closes the violation.

**For Platform:**

- KB stops drifting from live CDL (#1).
- One bounded EF surface (`cdl-<resource>-{read,write}`) per canonical resource, all with the same scope/tenant/audit contract — no per-Pipeline-feature bespoke EFs.
- Pattern B RLS rollout on `contact_listings` + `contact_listing_notes` (#4) sets the template for the rest of the Phase-2+ migration.

**For other apps (Atlas, future):**

- `mls-sync` stays admin-only (no change). Atlas continues to own that surface.
- New per-resource Pipeline EFs are general-purpose: any app with broker scope can use them (HRMS, ITSM, etc., if/when their domain expands to canonical RESO resources).

## Alternatives considered

- **Grant Pipeline `org_admin` scope on `mls-sync`** — rejected. `mls-sync` is an admin EF with no PII redaction, no per-resource tenancy logic for Pipeline, no per-broker filtering. Pipeline brokers are not org admins.
- **Direct anon writes from Pipeline to RLS-disabled tables** (`contact_listings`, `contact_listing_notes`, `properties`, `property_media`, `property_field_overrides`, `mls_*`) — rejected. Violates the [CDL access gate](../../product-specs/matrix-pipeline/wiki/architecture.md#compliance-gates). RLS-disabled means anyone with the anon key gets full r/w on all-broker, all-client data; the gate explicitly requires going through an EF with scope check.
- **Keep everything in CRM app DB permanently** — rejected. Violates the [Schema gate](../../product-specs/matrix-pipeline/wiki/architecture.md#compliance-gates). Canonical RESO resources must live in CDL once they have multi-app readers (e.g. `TransactionManagement` will be read by `matrix-fm` for variance reconciliation per [`wiki/integration.md#finance-erp-commission`](../../product-specs/matrix-pipeline/wiki/integration.md#finance-erp-commission)).
- **Ship the generic `cdl-write` EF first instead of per-resource EFs** — deferred. Per-resource EFs land sooner (each is small and well-scoped); the generic EF can be retrofitted later if the per-resource pattern proves too repetitive. Right now the per-resource cost is acceptable and the redaction/audit logic is resource-specific anyway.
