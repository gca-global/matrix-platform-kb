# ADR-033: Buyer-to-showing linkage as the `showing_participation` project-flavour resource (supersedes x_contact_key)

**Status**: Accepted
**Date**: 2026-06-15
**Deciders**: Pipeline team (matrix-pipeline 2.0) + platform team (CDL owners)
**Related**: [ADR-022](ADR-022.md) (superseded — the `x_contact_key` extension), [ADR-025](ADR-025.md) (project-flavour CRM resources `referral`/`document`), [ADR-016](ADR-016.md) (`cdl-write` dispatcher), [ADR-023](ADR-023.md) (`x_` extension prefix + retirement rule), [platform-extensions.md](../../data-models/platform-extensions.md), [cdl-schema.md](../../data-models/cdl-schema.md)

## Context

matrix-pipeline's showing lifecycle (FR-SHOW / showing-lifecycle.md) attaches a
**buyer Contact** to a showing so the broker can see *who* an appointment is for,
filter a buyer's showings on the engagement timeline, and roll a completed
showing forward into buyer-scoped follow-up.

[ADR-022](ADR-022.md) solved this by adding an `x_contact_key` platform
extension column to `public.showings`, `public.showing`, and
`public.showing_request`. While functional, this was the wrong shape:

- RESO DD 2.0 genuinely models **no Showing→Contact relationship** — the showing
  resources carry `ShowingAgentKey` (→ Member), never a buyer Contact.
- The platform convention ([platform-extensions.md](../../data-models/platform-extensions.md))
  is explicit: an `x_` extension is for a *missing field on an existing RESO
  resource*. **A wholly new relationship/entity that RESO does not model is NOT
  an extension** — it becomes a governed *project-flavour CDL resource* with
  plain canonical snake_case columns and its own ADR (exactly how `referral`,
  `document`, and `prospecting` were handled in [ADR-025](ADR-025.md)).
- Spreading the same `x_contact_key` across three RESO tables also duplicated the
  linkage and left the RESO Showing resources non-canonical.

This is part of the 2026-06 canonical-compliance pass that also retired the
`members.x_company` extension in favour of canonical `Member.OfficeName`.

## Decision

Model the buyer↔showing relationship as a **new project-flavour CDL resource**,
`public.showing_participation`, and **retire the `x_contact_key` extension**.

1. **New table `public.showing_participation`** (migration
   `20260615170000_showing_participation_resource.sql`), mirroring the
   `referral`/`document` source envelope: surrogate `id uuid` PK; natural key
   `unique(source_id, source_showing_participation_key)`;
   `is_visible`/`is_deleted`/`deleted_at` soft-delete; `locked_fields`/`raw`
   jsonb; full `originating_system_*`/`source_system_*` provenance;
   `created_at`/`updated_at` + `cdl_set_updated_at` trigger. Linkage columns:
   - `showing_key` — chain correlation key shared by `showing_request` /
     `showings` / `showing` (a single showing flows through all three under one
     `showing_key`).
   - `contact_key` — the buyer/witness Contact (`Contacts.ContactKey`), a loose
     RESO-key witness (no FK, consistent with the other `*_key` refs).
   - `participant_role text default 'Buyer'` (Buyer | CoBuyer | Attendee | …).
2. **Link at the `showing_key` (chain) level**, not per showing table. The app
   upserts one participation row per `(showing_key, contact_key)` with a
   deterministic source key `<showing_key>:<contact_key>` for idempotency across
   the request → appointment → showing steps.
3. **RLS: service-role-only at the table; EF-gated reads via `cdl-read`.** The
   resource links Contacts (PII-adjacent), so it has no anon/authenticated read
   — same posture as `referral`. Registered in both `cdl-write` (writable
   resource) and `cdl-read` (filterable `contact_key` / `showing_key`).
4. **`cdl-read` gains small array (`in`) filter support** so the contact-side
   engagement timeline resolves `contact_key → showing_key[]` in one call, then
   fetches `showings`/`showing` filtered by `showing_key: [...]` in a second.
5. **Drop the `x_contact_key` columns + indexes** on the three showing tables;
   the migration backfills `showing_participation` from the existing values
   first. The three RESO Showing resources are now canonically clean.

## Consequences

### Positive
- The three RESO Showing tables (`showing_request`/`showings`/`showing`) carry
  **zero** `x_` columns — they stay canonically pure.
- The buyer linkage is a single governed resource (not duplicated across three
  tables), extensible to additional roles via `participant_role`.
- Consistent with the established project-flavour pattern (`referral`/`document`,
  ADR-025) — no new precedent, no new EF.

### Negative / notes
- **Linkage is at `showing_key` granularity.** Today the Pipeline UI sets
  `showing_key = listing_key` for an app-authored chain, so two appointments on
  the same listing share a `showing_key`; buyer resolution picks the first Buyer
  participant per `showing_key`. If per-appointment buyer fidelity is later
  required, either mint a distinct `showing_key` per chain or extend
  `showing_participation` with a polymorphic `resource_name`/`resource_record_key`
  witness. Recorded as accepted residual.
- `contact_key` is a witness only (no FK) — orphaning is possible if a Contact is
  hard-deleted; acceptable for an engagement breadcrumb (same as ADR-022).
- The contact-side timeline now does a two-call (participant → showings) lookup
  instead of one filtered read; bounded by the new `in` filter and acceptable for
  a timeline panel.

## Alternatives considered
- **Keep `x_contact_key`** (ADR-022): rejected — violates the platform rule that
  a relationship RESO does not model is a project-flavour resource, not an `x_`
  extension; left three RESO tables non-canonical.
- **Join through `ContactListings`**: rejected — a showing is not always preceded
  by a `ContactListings` row, `showing_request` has no `listing_key`, and the
  many-to-one mapping is ambiguous; it would still need an `x_` witness.
- **Polymorphic `resource_name`/`resource_record_key`** on
  `showing_participation` (link to a specific showing row rather than the chain):
  deferred — simpler `showing_key`-level linkage matches how the chain correlates
  today; revisit if per-row fidelity is needed (see Negative notes).
