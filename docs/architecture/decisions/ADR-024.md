# ADR-024: CDL lookup-value normalization layer (canonical RESO StandardValues)

**Status**: Accepted
**Date**: 2026-06-05
**Deciders**: Platform team (CDL owners) + Pipeline/Atlas teams
**Related**: [ADR-014](ADR-014.md) (ingestion pipeline), [ADR-023](ADR-023.md) (`x_` extension prefix), [cdl-schema.md](../../data-models/cdl-schema.md) (lookup value normalization), [platform-extensions.md](../../data-models/platform-extensions.md) (PropertySubType), [canonical-compliance-audit-2026-06.md](../../product-specs/matrix-pipeline/canonical-compliance-audit-2026-06.md) (P6)

## Context

The 2026-06 canonical-compliance audit (P6) found that while RESO field/resource
**names** were canonical, the stored **values** of RESO closed-lookup columns were
not. `public.properties` held space-stripped / local tokens such as `CommercialSale`,
`FullService`, `ExclusiveAgency`, `SquareMeters`, `standard_apartment`,
`New Construction`, `Existing` — none of which are real
`reso_lookup_value_descriptions.standard_value`s. The FE classifiers (`listingKind`,
`applyListingKind`) were pinned to those non-canonical tokens, so the data layer and
FE were jointly off-standard. This is condition 2 of "100% RESO compliance": every
value in a closed-lookup column must be a real `StandardValue`.

Two write paths reach `public.properties`: the ingestion merge
(`reso-import → fn_apply_field_mapping → fn_merge_listings`) and the Atlas
`mls-sync upsert-resource` form write. `fn_apply_field_mapping` is the documented
ingestion choke point but does **not** see the Atlas form-write path.

## Decision

Introduce a **value-normalization layer at the `public.properties` /
`public.properties_published` write boundary**, plus a value guard:

1. **`public.reso_lookup_value_map`** — authoritative, runtime-consumed map
   `(source_id, lookup_name, lower(source_value)) → standard_value`; `source_id='*'`
   = all sources. Seeded for `PropertyType`, `PropertySubType`, `ListingService`,
   `ListingAgreement`, `LotSizeUnits`, `DevelopmentStatus`.
2. **`public.cdl_normalize_lookup_value(lookup_name, source_id, raw)`** — resolution:
   source-scoped map → global map → case-insensitive corpus match (casing only) →
   passthrough.
3. **`tg_properties_normalize_lookups`** — BEFORE INSERT/UPDATE trigger on both
   tables. Normalizes the six columns and couples `development_status`
   `New Construction`/`Existing` → `new_construction_yn` (those are not RESO
   `DevelopmentStatus` values; both map to `Completed`).
4. **`tg_properties_validate_lookups`** — BEFORE trigger (fires after normalize)
   that rejects any remaining non-`StandardValue` closed-lookup value.

A one-time backfill normalized existing rows. The Atlas FE enums/types/classifiers
were flipped to canonical values in lock-step (with a transitional dual-accept across
the deploy window).

### Why a trigger, not `fn_apply_field_mapping`

A BEFORE trigger on `properties` is the single point that covers **both** write
paths (ingestion merge and Atlas form write), and it composes with the value guard
(normalize → validate in one statement). FMA only covers ingestion. The FMA `text`
lookup expressions and the hardcoded `'SquareMeters'` in `fn_merge_listings` are left
in place but rendered harmless by the trigger. Legacy `mls-sync/index.ts` TS mappers
were aligned to emit canonical RESO as defence-in-depth.

## RESO divergence (KB-first escape hatch)

- **`property_sub_type` is mapped lossily to the nearest RESO `PropertySubType`.**
  The Cyprus local vocabulary (`penthouse`, `studio`, `villa`, `bungalow`, `plot`,
  `field`, …) has no RESO equivalent; rather than carry `x_*` subtype extensions, the
  local granularity is **intentionally dropped** at storage (penthouse/studio →
  `Apartment`, villa/bungalow → `Single Family Residence`, plot/field →
  `Unimproved Land`, …). Recorded in `platform-extensions.md`. Re-introducing local
  granularity later would be a governed `x_property_subtype_local` column, not a
  silent value.
- **`DevelopmentStatus` `New Construction`/`Existing` are dropped.** They are not RESO
  values; the new-vs-resale signal lives in `new_construction_yn` + `property_condition`.

## Consequences

### Positive
- Stored closed-lookup values are now 100% canonical (0 non-canonical verified); the
  guard keeps it permanent across both write paths.
- The FE no longer pins to non-canonical tokens; the data layer is the source of truth.

### Negative / notes
- A genuinely new, unmapped source lookup value is **rejected on write** until a
  `reso_lookup_value_map` row is added — a deliberate "fail loud" trade-off for
  compliance. Monitor ingestion for `check_violation` on these columns.
- `property_sub_type` local detail is lost (by decision); downstream consumers that
  need it must use a future governed extension.
- The transitional dual-accept in `listingKind`/`applyListingKind` is to be removed
  once the backfill+deploy window is confirmed.

## Alternatives considered
- **Wire normalization into `fn_apply_field_mapping`** — rejected: misses the Atlas
  form-write path and requires risky reproduction of two large SQL functions.
- **Hardcoded CHECK constraints** — rejected: a CHECK cannot subquery the corpus
  table, and a hardcoded IN-list would drift from `reso_lookup_value_descriptions`.
- **Carry local subtypes as `x_*` extensions** — rejected per user decision
  (nearest-only, lossy) to keep the closed lookup strictly RESO.
