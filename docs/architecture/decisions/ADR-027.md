# ADR-027: Console-managed Third-Party Auth provisioning for own-DB apps

**Status**: Accepted
**Date**: 2026-06-09
**Deciders**: Platform team (SSO owners)
**Related**: [ADR-018](ADR-018.md) (SSO issuer + Supabase Third-Party Auth for own-DB apps), [ADR-011](ADR-011.md) (ES256 signing), [ADR-012](ADR-012.md) (dedicated CDL project / no app service-role key), [ADR-019](ADR-019.md) (server-managed PKCE), [app-template.md](../../platform/app-template.md), [sso-edge-functions.md](../../platform/sso-edge-functions.md)

## Context

Per ADR-018, every own-DB Matrix app must register a **Third-Party Auth (TPA)**
integration on its App DB Supabase project (SSO issuer + JWKS) so PostgREST
trusts the SSO-issued ES256 token; without it every App DB query returns
`401 PGRST301`.

Until now this was provisioned **per app, from inside Lovable**, by a throwaway
`bootstrap-tpa` Edge Function that called the Supabase Management API using an
`ACCOUNT_ACCESS_TOKEN` secret — a **Supabase Personal Access Token (PAT)** the
builder generated, set as a secret, then was meant to delete + rotate. This has
real problems:

- **It puts an account-level Management PAT in the hands of every app builder /
  business user** ("vibe coders"), who must generate, store, and remember to
  revoke it. High friction, easy to get wrong, and a standing credential risk if
  the function/secret is left deployed.
- **It is per-app boilerplate** (function source, `config.toml` entry, secret)
  duplicated across every remix, with no central record of which apps are
  actually provisioned.
- **No status visibility** — nothing on the SSO side records whether an app's DB
  trusts SSO, when, or why a provisioning attempt failed.

The SSO Console already manages `sso_applications` (register, edit, rename
`client_id`, server-managed PKCE) via the `admin-apps` Edge Function, which runs
with `rw_global` admin auth and `verify_jwt: false`. The user confirmed a single
platform PAT can administer all app Supabase projects.

## Decision

Move TPA provisioning into the **SSO Console**, server-side, behind one
platform-held PAT.

1. **Schema** (`sso_applications`, migration `20260609180000_app_tpa_provisioning`):
   add `app_supabase_project_ref`, `tpa_status` (`null | provisioned | failed`),
   `tpa_provisioned_at`, `tpa_integration_id`, `tpa_last_error`.
2. **One platform PAT** stored once in the **SSO Vault** as
   `sso_supabase_management_pat` (vault names are exempt from the `SUPABASE_`
   env-prefix restriction), read via the existing `get_vault_secret(secret_name)`
   RPC — same pattern as `sso_es256_signing_key`. No app ever holds it.
3. **`admin-apps` EF** gains:
   - `POST /admin-apps/{id}/provision-tpa` — body `{ project_ref?, reload? }`.
     Resolves the ref (body / pasted `https://<ref>.supabase.co` / stored
     column), reads the Vault PAT, calls the Management API
     `…/config/auth/third-party-auth`. Idempotent (skip if the SSO issuer is
     already registered); `reload` does DELETE + POST to force a Data-API reload.
     On success records `provisioned` + integration id and sets
     `jwt_secret_name = NULL` (so `oauth-token` mints ES256 — the TPA-trusted
     alg). On failure records `failed` + `tpa_last_error`.
   - `GET /admin-apps/{id}/tpa` — returns the stored status + ref.
   - create/update accept `app_supabase_project_ref`.
4. **Console UI**: the create dialog takes an optional App DB project ref; the
   Edit App dialog gains a **Third-Party Auth (App DB)** section — status badge,
   ref input, **Provision TPA** button, **Force Data-API reload** toggle, and
   last-error display.
5. **Apps install nothing.** A business user just gives their Matrix admin the
   App DB project ref (found in `VITE_SUPABASE_URL`); the admin clicks Provision
   once. App templates (`WelcomeSetup.tsx`, `.lovable/instructions.md`) point at
   the Console action and **demote `bootstrap-tpa` + `ACCOUNT_ACCESS_TOKEN` to a
   deprecated fallback** for environments that cannot reach the Console.

## Consequences

- **No account PAT in builders' hands.** One platform PAT lives in the SSO Vault;
  rotation is a single operation. Least-privilege improvement over per-app PATs.
- **Central status + audit.** `sso_applications` records which apps trust SSO,
  when, the integration id, and the last error — visible in the Console.
- **Less per-app boilerplate.** New apps don't ship a bootstrap function or a
  TPA secret. The deprecated fallback remains only for offline/edge cases.
- **Idempotent + recoverable.** Re-provisioning is safe; the Force reload toggle
  clears a lingering `401 PGRST301` without manual Management API calls.
- **Trust assumption.** The platform PAT must be able to administer every app's
  Supabase project (confirmed: single org). If app projects move under separate
  orgs, this needs per-org PATs (keyed off `app_supabase_project_ref`).
