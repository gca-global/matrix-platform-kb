# ADR-022: Buyer-to-showing linkage as a Sharp Matrix platform extension (x_contact_key)

**Status**: Accepted
**Date**: 2026-06-05
**Deciders**: Pipeline team (matrix-pipeline 2.0) + platform team (CDL owners)
**Related**: [ADR-016](ADR-016.md) (cdl-write dispatcher / junction retirement), [ADR-023](ADR-023.md) (`x_` extension prefix), [platform-extensions.md](../../data-models/platform-extensions.md) (x_ convention)

> **Prefix update (2026-06-05):** this column shipped as `x_sm_contact_key` and was renamed to `x_contact_key` by migration `20260605160000_rename_x_sm_extensions_to_x.sql` when the platform adopted the `x_` prefix ([ADR-023](ADR-023.md)). References below use the current name.

## Context

matrix-pipeline's showing lifecycle (FR-SHOW / showing-lifecycle.md) attaches a
**buyer Contact** to a showing so the broker can see *who* an appointment is for,
filter a buyer's showings on the engagement timeline, and roll a completed
showing forward into buyer-scoped follow-up.

The canonical CDL showing tables —
`showing_request`, `showings` (RESO ShowingAppointment), and `showing`
(RESO Showing, the recorded fact) — were created in
`20260529160000_pipeline_canonical_new_tables.sql` strictly from RESO DD 2.0,
which has **no `ShowingContactKey`** (RESO models the *requesting agent* and the
*listing*, not a buyer contact). The Pipeline UI and `EngagementTimeline.tsx`
nonetheless wrote and filtered by a `contact_key` on these tables — a column
that was never created. Result: every showing-chain insert that carried the
buyer 400'd, and the contact-side engagement timeline read returned nothing.

## Decision

Add a **Sharp Matrix platform extension column** `x_contact_key text` to
`public.showings`, `public.showing`, and `public.showing_request`, carrying the
buyer's `Contact.ContactKey` (a loose RESO-key witness, consistent with the
other `*_key` cross-resource references on these tables — no hard FK).

- Naming follows the **`x_` extension convention** (platform-extensions.md):
  the field has no RESO DD 2.0 equivalent, so it must not masquerade as a
  canonical RESO column. This is why the demo's `contact_key` payloads were
  rejected/renamed rather than a bare `contact_key` column being added.
- Each column is indexed and added to the `cdl-read` filterable allow-list so
  the contact-side engagement timeline can filter showings by buyer.
- The Pipeline app writes/reads `x_contact_key` (was `contact_key`) in
  `useShowingChain.ts` and `EngagementTimeline.tsx`.

Landed in `20260605120000_pipeline_week3_write_fixes.sql` (CDL).

## Consequences

### Positive
- Buyer-linked showings work end-to-end (write + contact-side timeline read).
- The extension is honestly flagged as non-RESO, so outbound RESO/Dash channels
  never mistake it for a canonical field (it is not exported).
- Consistent with the existing loose-witness pattern on the showing tables.

### Negative / notes
- One more `x_` column to carry through any future RESO-purity audit; if a
  later RESO DD version adds a buyer-contact concept, migrate per the
  platform-extensions retirement rule.
- `x_contact_key` is a witness only (no FK) — orphaning is possible if a
  contact is hard-deleted; acceptable for an engagement breadcrumb.

## Alternatives considered
- **Reuse a bare `contact_key`** — rejected: violates the `x_` rule for
  non-RESO fields and would imply a canonical RESO field that does not exist.
- **Join through ContactListings** — rejected: a showing is not always preceded
  by a ContactListings row, and the timeline filter needs a direct column.
