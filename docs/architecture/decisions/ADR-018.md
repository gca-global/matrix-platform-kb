# ADR-018: SSO issuer URL + Supabase Third-Party Auth for own-DB apps (ES256 completion)

**Status**: Accepted
**Date**: 2026-05-31
**Extends**: [ADR-011](ADR-011.md) (ES256 JWT signing), [ADR-002](ADR-002.md) (dual-Supabase)

## Context

ADR-011 migrated SSO JWT signing to **ES256** and listed, as a *"Next"* step,
*"import the ES256 public key into each app's Supabase project."* Apps that use
their **own** Supabase project (`matrix-pipeline`, `matrix-atlas-mls`,
`matrix-mls` — all on app DB `wckwfbbqiupvallmhqbu`) read app-local tables
(`role_configurations`, `notifications`) via **direct PostgREST**. PostgREST only
trusts keys registered in that project, so it could not verify SSO-issued ES256
tokens.

These three apps had `sso_applications.jwt_secret_name = null`, which the minters
treat as *"sign ES256"*. The result: every token was ES256 (kid `dab1e43f`), but
the app DB's JWKS held only its own key (`393e0d85`) plus a legacy HS256 key
(`281ceba0`). So SSO ES256 tokens were rejected with `401`; the only tokens that
ever validated were the occasional HS256-fallback tokens (signed with the shared
legacy secret the app DB still trusts). When ADR-011's reliability fix removed the
silent HS256 fallback (ES256-or-fail-closed), the app DB calls became a
**consistent 401** — surfacing the long-standing, never-completed key-trust gap.

Two mechanisms were evaluated to make the app DB trust SSO ES256 tokens:

1. **Import the SSO key as a project signing key** — rejected. The Management API
   `POST .../signing-keys` requires the **private** key (`d`). Importing the SSO
   private signing key into an app DB would let that project mint SSO tokens for
   *any* app — unacceptable secret sprawl.
2. **Supabase Third-Party Auth (TPA)** — the correct verify-only mechanism. PostgREST
   verifies tokens whose `iss` matches a registered `oidc_issuer_url`, using that
   integration's JWKS. **But** Supabase TPA requires a **URL** issuer, and SSO minted
   `iss: "matrix-sso"` (a bare string), so TPA could not be registered for it.

## Decision

**Make the SSO a proper OIDC-style issuer and register it as Third-Party Auth on
own-DB app projects.**

1. **SSO tokens now set `iss` = the SSO project's GoTrue issuer URL**
   `https://xgubaguglsnokjyudgvc.supabase.co/auth/v1` (was `"matrix-sso"`), in all
   minting functions: `oauth-token` (initial + refresh), `switch-role`,
   `switch-tenant`. The SSO project's `/auth/v1/.well-known/jwks.json` already
   serves the ES256 signing key `dab1e43f` (registered as a standby key).
2. **App DB `wckwfbbqiupvallmhqbu` registers a TPA integration**: `oidc_issuer_url`
   = the SSO issuer URL, `jwks_url` = the SSO `.well-known/jwks.json`. PostgREST
   then natively verifies SSO ES256 tokens, returning `200` for Pipeline / Atlas /
   Matrix MLS at once. No private key leaves the SSO project.

### Why changing `iss` is safe

Audit (2026-05-31) found **no consumer verifies `iss == "matrix-sso"`**: it is set
only at the four mint sites; no SSO/CDL Edge Function, app SSO client, or RLS
policy checks it. Verifiers validate by **signature/JWKS** (and the `role`/scope
claims), not by issuer string. The other `issuer` references in the codebase are
the Microsoft AD identity issuer, which is unrelated.

## Consequences

### Positive
- Own-DB apps verify SSO ES256 tokens **natively via PostgREST** — completes the
  ADR-011 "Next" step without HS256 or secret sharing.
- One TPA integration fixes all apps on the shared app DB (Pipeline, Atlas, MLS).
- Key rotation propagates automatically (TPA re-resolves the SSO JWKS).
- The SSO now behaves as a standard OIDC issuer (URL `iss` + discoverable JWKS),
  unlocking the same pattern for every other own-DB app project.

### Negative / transition
- Tokens minted **before** the `iss` change still carry `iss: "matrix-sso"` and
  will not match the TPA until they expire / are refreshed (users re-login or the
  proactive refresh re-mints). Transient during rollout only.
- Each remaining own-DB app project (HRMS, ITSM, FM, etc.) must register the same
  TPA integration before its `jwt_secret_name` can be set to `null` (ES256). Until
  then those apps stay on HS256 (`jwt_secret_name` set) — unchanged by this ADR.

## Unified verification model (2026-06-01)

All three projects that receive an SSO ES256 token now verify it against the
**same SSO JWKS** (`https://xgubaguglsnokjyudgvc.supabase.co/auth/v1/.well-known/jwks.json`,
signing `kid dab1e43f`):

| Project | Mechanism |
|---|---|
| SSO `xgubaguglsnokjyudgvc` | GoTrue **standby key** (verifies its own tokens; no TPA needed) |
| App DB `wckwfbbqiupvallmhqbu` | **Third-Party Auth** → SSO JWKS |
| CDL `ofzcokolkeejgqfjaszq` | **Third-Party Auth** → SSO JWKS (added 2026-06-01) |

RLS is the primary access control on all three; Edge Functions are reserved for
PII owner-clamp, writes, and service-role/cross-cutting work (`verify_jwt=false`
+ in-code verification). The browser attaches a **fresh** token per request via
the shared `postgrestAccessToken` hook (`matrix-pipeline-2-0/src/lib/matrix-sso.ts`):
it refreshes on expiry (single-flight) and returns `undefined` (anon fallback)
when no session exists, so PostgREST never receives an expired/empty bearer.

## Key-rotation runbook (keep N and N+1 valid)

The SSO JWKS already serves multiple ES256 keys, so consumers can verify both
the current and the next signing key during a rotation. To rotate without an
outage:

1. **Publish** the new ES256 **public** key to the SSO GoTrue **standby** key set
   (it appears in `.well-known/jwks.json` alongside the current key). Do *not*
   switch signing yet. (Public-only keys cannot be added via
   `config/auth/signing-keys` — they must enter via the standby/JWKS path.)
2. **Re-resolve TPA** on every consumer project (App DB, CDL) — `DELETE` then
   `POST` the same integration body to force a **Data-API reload** (see gotcha
   below). Confirm `resolved_jwks` now lists **both** the old and new `kid`.
3. **Verify with live requests** that a token signed by the *old* key still
   returns `200` everywhere (no premature cutover).
4. **Switch signing** to the new key (rotate the `sso_es256_signing_key` vault
   secret / promote the standby to in-use). New tokens carry the new `kid`;
   already-issued old-`kid` tokens keep verifying until they expire.
5. **Retire** the old key from the standby set only after the longest token TTL
   has elapsed, then re-resolve TPA once more.

The platform health probe (`~/tmp/sso_health_probe.mjs`, see
[sso-edge-functions.md](../../platform/sso-edge-functions.md)) mints a live token
and curls each project's PostgREST + critical EFs — run it after each step to
catch a `PGRST301` regression immediately.

## Operational gotcha — TPA does not take effect until the Data API reloads

Registering the TPA via `POST .../config/auth/third-party-auth` **resolves the
JWKS immediately** (the integration shows a populated `resolved_jwks` with
`dab1e43f`), but that **does not guarantee PostgREST (the Data API) starts
verifying tokens against it.** After the initial registration, the app DB kept
returning `401 PGRST301 "No suitable key or wrong key type"` for a correctly
signed SSO ES256 token whose `kid` was present in `resolved_jwks` — i.e. the
config was perfect but the running Data API had not loaded it.

**Fix / verification step:** re-register the integration (`DELETE` then `POST`
the same body). The re-registration forces a Data-API config reload; within
~60–90 s PostgREST verifies the SSO ES256 token and returns `200`. Always
**confirm with a live request** (a raw `curl` to a protected table with a real
SSO token, *the full untrusted token string — do not trim claims or the
signature check fails*), not just by inspecting the TPA's `resolved_jwks`.

> First-mover note: the 2026-05-13 HRMS-sandbox TPA was never exercised with a
> real ES256 SSO token (HRMS still signs HS256), so this reload requirement was
> only discovered here. Importing the SSO **public** JWK as a `standby`
> signing key is **not** an alternative — `POST .../config/auth/signing-keys`
> with a public-only key returns HTTP 400.
