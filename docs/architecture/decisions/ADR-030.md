# ADR-030: Promote the transaction linkage from `HistoryTransactional.raw` to a governed `x_transaction_key` extension

**Status**: Proposed (implementation pending — CDL migration + `cdl-listing-lifecycle`/`cdl-read` + app)
**Date**: 2026-06-10
**Deciders**: Platform team (CDL owners) + Pipeline team
**Related**: [ADR-026](ADR-026.md) (event-sourced transaction model — this ADR refines its decision #4 link mechanism), [ADR-022](ADR-022.md) (`x_contact_key` — the precedent: RESO-gap linkage as a governed `x_` extension), [ADR-023](ADR-023.md) (`x_` prefix), [platform-extensions.md](../../data-models/platform-extensions.md), [transaction-lifecycle.md](../../business-processes/canonical-processes/processes/transaction-lifecycle.md)

## Context

RESO DD 2.0 defines `TransactionManagement` as a **bare 4-field header** (`TransactionKey`, `TransactionId`, `TransactionType`, `ModificationTimestamp`) with **zero foreign keys**, and provides **no canonical linkage** between a transaction and its property, buyer, documents, or commission — verified against the live standard (`dd.reso.org/DD2.0/TransactionManagement/`, generated 2026-06-08; `fields.csv` shows `TransactionKey`/`TransactionId` exist on no other resource; `relationships.csv` has zero transaction entries). Additionally, `HistoryTransactional.ResourceName` is a **closed 5-value lookup** (`Property`, `Member`, `Office`, `Contacts`, `Association`) that does **not** include `TransactionManagement`, so a history event cannot canonically anchor *on* a transaction.

ADR-026 (decision #4) therefore carried the transaction context **inside `HistoryTransactional.raw`** as `{transaction_key, contact_key}` — chosen specifically to avoid adding columns. In practice this means the link between a transaction-phase event and its `TransactionManagement` identity lives in a **free-form JSON blob**:

- it is not a first-class, indexed, queryable column;
- "which events belong to transaction X" requires JSON extraction (`raw->>'transaction_key'`);
- it is invisible to schema-level tooling, the `cdl-read` filterable allow-list, and RESO-purity audits.

For a project whose discipline is "canonical RESO DD where RESO defines it; a **governed, explicit extension** where RESO is silent", burying the only transaction-identity link in `raw` is the weakest available form of extension. The canonical-clean tool for exactly this situation already exists and has a precedent: ADR-022 added `x_contact_key` to the showing tables because RESO models no buyer→showing link, and rejected "join through ContactListings" precisely because **the timeline filter needs a direct, indexed column**.

Note the scope boundary already recorded in `platform-extensions.md`: the **transaction buyer** is NOT modeled with `x_contact_key` — it uses the canonical `ContactListings` junction (`contact_key` + `listing_key`) per ADR-026. This ADR does not change that. It is solely about the **transaction-identity** link in the event spine.

## Decision

Promote the transaction-identity link out of `HistoryTransactional.raw` into a **governed platform extension column** `x_transaction_key text` on `public.history_transactional` (CDL), carrying the `TransactionManagement.TransactionKey` of the transaction-phase event.

1. **Naming & governance** follow the `x_` convention (ADR-023, platform-extensions.md): `TransactionManagement` linkage has no RESO DD 2.0 equivalent on `HistoryTransactional`, so it must not masquerade as a canonical column. Loose RESO-key witness (no hard FK), consistent with the existing `*_key` cross-resource references and with `x_contact_key`.
2. **Indexed** and added to the `cdl-read` filterable allow-list, so "the timeline / documents / events for transaction X" is a first-class indexed read, not a JSON scan.
3. **Not exported** to any outbound RESO/Dash/IDX channel (like all `x_` columns).
4. **`cdl-listing-lifecycle`** writes `x_transaction_key` on the `HistoryTransactional` events it emits (`acceptOffer`/`closeDeal`/`cancelDeal`), in addition to (transitionally) `raw` for backward compatibility.
5. **Buyer stays canonical**: `contact_key` continues to resolve through `ContactListings` (ADR-026). The buyer is NOT promoted to an `x_` column. `raw.contact_key` may remain as event payload, but is not the queryable buyer link.
6. **`TransactionManagement` stays the bare canonical RESO header** — unchanged, no link columns added to it (ADR-026 #3 preserved). The extension lives on the *referencing* event row, not on TM.
7. **Already-first-class references are unaffected**: `commission_estimate.transaction_key` and `document.related_resource='TransactionManagement'`/`related_key` are app-private typed columns and already satisfy the "explicit, not in `raw`" bar; no change needed there.

## Migration path (implementation, pending)

- CDL migration (`matrix-platform-foundation/supabase-cdl/migrations/`): add `x_transaction_key text` + index on `public.history_transactional`; backfill from `raw->>'transaction_key'` where present.
- `cdl-listing-lifecycle` EF: write `x_transaction_key` on emitted events (keep `raw` during transition).
- `cdl-read`: add `x_transaction_key` to the `history_transactional` filterable allow-list.
- App (`matrix-pipeline-2-0`): read/filter by `x_transaction_key` in `useTransactions.ts` instead of parsing `raw`.
- KB: `platform-extensions.md` (new Showing-sibling "Transaction Extensions" row), `transaction-lifecycle.md` (link mechanism note), this ADR.

Until the migration lands, `raw.transaction_key` remains the source of truth; afterward, `raw` is a transitional fallback and `x_transaction_key` is authoritative for reads.

## Consequences

### Positive
- The transaction-identity link is now an **explicit, governed, indexed extension** — honest about being non-RESO (RESO defines no such link), instead of hidden in a JSON blob. Resolves the "we're canonical but the link is in `raw`" tension.
- First-class, indexable reads for "events / documents / commission for transaction X"; no JSON extraction on the hot path.
- Consistent with the ADR-022 precedent and the platform's extension governance; `TransactionManagement` remains the untouched canonical RESO header.

### Negative / notes
- One more `x_` column to carry through future RESO-purity audits; retire per the platform-extensions retirement rule if a later RESO DD version models transaction linkage.
- Transitional dual-write (`raw` + `x_transaction_key`) until backfill completes and the app cuts over.
- `x_transaction_key` is a witness only (no FK); orphaning is possible if a transaction row is hard-deleted — acceptable for an event-spine breadcrumb (same posture as `x_contact_key`).

## Alternatives considered
- **Keep the link in `raw` (ADR-026 as-built)** — rejected here: legitimate as event payload, but not first-class/queryable and invisible to schema tooling; weakest extension form for a canonical-disciplined project.
- **Add link columns to `TransactionManagement`** — rejected (as in ADR-026): invents non-canonical FKs on a RESO-bare header.
- **Drop `TransactionManagement` entirely** — rejected: removes a real RESO resource and its canonical `TransactionType`, forces a non-RESO surrogate deal-id, and does not make the project more canonical (RESO leaves transaction linkage undefined regardless).
- **Model the buyer with `x_transaction_key`'s sibling `x_contact_key` on history** — rejected: the buyer has a canonical home (`ContactListings`); only the transaction identity lacks one.
