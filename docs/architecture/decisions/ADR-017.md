# ADR-017: Browser SSO token storage — localStorage now, BFF/httpOnly as the remediation path

**Status:** Accepted (documents a known, accepted risk)
**Date:** 2026-05-31
**Deciders:** platform team (SSO owners) + Pipeline team (matrix-pipeline 2.0)
**Related:** ADR-002 (dual-Supabase), ADR-007 (Edge Functions), ADR-008 (5-level scope), ADR-011 (ES256 JWT signing)
**Supersedes:** —
**Superseded by:** —

## Context

Matrix apps authenticate against the SSO project via OAuth 2.1 Authorization Code
+ PKCE (the canonical client flow lives in each app's `src/lib/matrix-sso.ts`).
An SSO-flow audit (2026-05-31, matrix-pipeline 2.0) confirmed the client is
otherwise canonical and well-hardened:

- Authorization Code + PKCE (`S256`), 256-bit crypto-random verifier (not a UUID).
- Strict `state` CSRF validation on the callback.
- Refresh-token rotation enforced (RFC 9700 §4.13): a refresh response without a
  new refresh token is treated as a protocol failure and clears the session.
- Cross-tab refresh serialization via Web Locks + single-flight de-dup.
- PKCE artifacts in per-tab `sessionStorage` (RFC 8252), no localStorage fallback.
- ES256 (ADR-011); implicit flow removed; proactive pre-expiry refresh.

The one residual gap is **token storage**: the access token and refresh token are
held in `localStorage` (`matrix_sso_access_token` / `matrix_sso_refresh_token`).
`localStorage` is readable by any JavaScript running on the origin, so an XSS
vulnerability or a compromised front-end dependency (supply-chain) can exfiltrate
both tokens.

The current industry best practice (IETF *OAuth 2.0 for Browser-Based Apps*,
Duende, Auth0/Okta) for business/sensitive apps is the **Backend-for-Frontend
(BFF)** pattern: a confidential server-side client performs the code exchange,
stores tokens server-side, and the browser holds only a `__Host-`, `HttpOnly`,
`SameSite` session cookie — tokens never reach JavaScript. Note that Supabase's
own non-SSR default is also `localStorage`, so the current implementation matches
the framework norm but not the strongest posture.

## Decision

1. **Accept `localStorage` token storage for now** as a known risk. It matches the
   Supabase non-SSR default and is bounded by the existing hardening (PKCE,
   `state`, RT rotation, ES256, short access-token TTL). This avoids a large,
   cross-app, server-side change under time pressure.
2. **Record the remediation path** as the future direction: introduce a BFF /
   cookie-setting SSO Edge Function so the browser only holds an `HttpOnly`
   session cookie and tokens are never exposed to JS. This is a platform-level
   change (SSO Edge Functions + per-app integration) and is explicitly **out of
   scope** for the app-side `matrix-sso.ts` / callback work.
3. **Compensating controls** to keep in force meanwhile: strict CSP, dependency
   review/SRI for third-party scripts, short access-token lifetime with rotation,
   and server-side verification of every token (APIs never trust the client).

## Consequences

- No client code change in this release for token storage; the canonical
  in-scope improvements (base-path agnostic redirect URI, callback auto-recovery,
  cached-user fast path, `openid` scope) ship independently.
- The XSS/supply-chain exfiltration risk remains until the BFF/cookie path is
  built; it is now tracked rather than silent.
- When the BFF path is adopted, `matrix-sso.ts` storage and refresh logic move
  server-side; apps switch to cookie-based session calls.

## Alternatives considered

- **Move tokens to in-memory only (no persistence):** rejected for now — breaks
  reload/multi-tab session continuity without a server session to rehydrate from,
  and still exposes tokens to XSS while live.
- **Encrypt tokens in `localStorage`:** rejected — the decryption key must also
  live in JS, so it does not meaningfully resist XSS (security theatre).
- **Adopt BFF immediately:** deferred — correct end state, but requires
  cross-app server-side work (SSO Edge Functions, cookie domain/session store)
  beyond the current app-only scope.
