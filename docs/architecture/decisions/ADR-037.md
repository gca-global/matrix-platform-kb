# ADR-037: Interactive term definitions — Qobrix → RESO → custom glossary with click-through sidebar

**Status**: Accepted  
**Date**: 2026-07-12  
**Deciders**: Sharp SIR sales-automation team (matrix-qobrix-sales-automation-v1-0) + platform team  
**Related**: [ADR-036](ADR-036.md) (Qobrix-vanilla-inside + label layer), [ADR-020](ADR-020.md) (per-tenant/locale overrides), [ADR-021](ADR-021.md) (runtime DB i18n), [ADR-005](ADR-005.md) (RESO DD as interop layer)

## Context

ADR-036 made the app **drift-free** inside (Qobrix vanilla identifiers + `x_` extensions + app-local labels). Business users still disagree on how to *name and define* domain terms (pipeline stage, listing vs property vs project, lead vs opportunity). That disagreement must not leak into the data model, EFs, or frontend identifiers — it belongs in the **label/definition layer**.

Users also need an in-app way to **agree on meaning**: not only rename a label, but attach a shared definition that everyone can open while working.

## Decision

### D1 — Every labeled term may carry a definition

`public.ui_terminology.description` is the corpus for definitions (already existed). The runtime `app-i18n` EF serves definitions under source-agnostic namespaces (see D6):

- `def.<Resource>.<field>` / `defEnum.<Resource>.<field>.<code>`
- `def.glossary.<TermId>` for concept terms (paired with `label.glossary.<TermId>`)

### D2 — Label + definition source priority: Qobrix → RESO DD → custom

Build-time resolver (`scripts/gen_term_definitions.mjs`) resolves **both** the display label and the definition independently via the same chain, tagging each with provenance (`label_source`, `description_source`):

1. **Qobrix** OpenAPI (humanized field name for vanilla labels; field description when present)
2. **RESO DD 2.0** via alias map (`qobrix-reso-alias.json`) or PascalCase auto-match against vendored `src/i18n/reso-dd-definitions.json` (displayName + definition)
3. **Custom** only if both are silent (`docs/qobrix-vanilla/custom-term-definitions.json`)

Qobrix always wins when it defines a term. RESO fills gaps. Custom fills app concepts (Lead, Project, PipelineStage, Collection, …) and remaining extension gaps. The UI never branches on source — provenance is recorded in the DB and shown only in admin surfaces.

### D3 — Definitions mode + click-through term sidebar

A per-user **Definitions mode** toggle (top bar, localStorage) reveals a circle-i icon next to labeled terms (`QobrixFieldLabel`, `GlossaryTerm`). Clicking it opens the app's **standard right-side Sheet** (`TermDetailSheet`):

- shows key, **label_source** + **description_source** provenance badges, label, definition
- **admins** (`system_admin` | `org_admin`) edit label + definition inline via `app-label-admin` (tenant overrides) with live `reloadI18n`
- non-admins get a read-only explanation
- **Change history** section lists who changed what, from → to, and when (`ui_label_history`)

The same sidebar is opened from Settings → Translations & Labels (terminology rows), unifying read (explain) and write (govern). Interface-text rows have a per-row History affordance for the same audit trail.

### D4 — Coverage is advisory, not blocking

Comprehensive seeding attempts a definition for every corpus row; many Qobrix-only fields have neither Qobrix desc nor RESO analog (~34% defined at first cut). Undefined terms simply show no icon (or open an empty authorable sheet for glossary). `check_term_coverage.mjs` reports coverage and never fails CI.

### D5 — Circle-i surface rollout (product UI)

The circle-i only renders inside `QobrixFieldLabel` / `GlossaryTerm`. A later pass rolled those wrappers across Leads, Pipeline, Offers, Contacts, Listings, Approvals, Contract/Offer wizards, and sidebar nav concept nouns so Definitions mode lights up icons where agents actually work.

Client-side field resolution is casing-agnostic (`exact` → RESO reverse-alias via `src/i18n/reso-field-alias.json` → PascalCase→snake_case) so CDL/RESO-named call sites (e.g. `City`, `ListPrice`) resolve to Qobrix snake corpus keys.

**Deferred follow-up:** dynamic field rows in My Day, ContactProfile overview chips, and listing `FullDetailsSection` / `field-display.ts` still render plain strings — GlossaryTerm-only for concept nouns where applicable; field-level icons there need a separate pass.

### D6 — Source-agnostic runtime namespaces (supersedes earlier `qobrix*`/`x*` split)

ADR-036 D8 + this decision: storage uses **bare** `resource` values; runtime bundle uses only `label` / `labelEnum` / `def` / `defEnum`. The previous `qobrix.*` / `x.*` / `*Def` / `glossary*` fan-out and the `vanilla`/`extension` source badge are retired. Extension vs vanilla is still discoverable via the `x_` field prefix and the provenance columns.

### D7 — Runtime change audit

`public.ui_label_history` records every tenant upsert/delete on both corpora (`ui_terminology` and `app_ui_string`): actor (SSO sub/name/email), action, locale, old → new values, timestamp. Written only by `app-label-admin` (service role); RLS deny-all for anon/authenticated. Tenant-scoped reads via the `history` action.

## Consequences

### Positive
- Data model / EF / FE identifiers stay vanilla; business naming fights stay in the label layer.
- The running app becomes an interactive glossary and the common source of truth for term meaning.
- RESO provides high-quality industry definitions without making RESO a live UI namespace (ADR-036).
- One label + one definition per term — no source-branching complexity for the UI.
- Full who/what/from→to/when audit of runtime terminology edits.

### Negative / notes
- Partial coverage until custom authoring fills gaps.
- Vendored RESO text is subject to the RESO EULA; regenerate from the KB corpus / official sheets as needed.
