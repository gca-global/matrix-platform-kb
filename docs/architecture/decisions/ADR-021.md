# ADR-021: Runtime, DB-driven i18n — single bundled English baseline + CDL `app_ui_strings` corpus (platform standard)

**Status**: Accepted
**Date**: 2026-06-02
**Extends**: [ADR-012](ADR-012.md) (dedicated CDL project, separate from SSO), [ADR-020](ADR-020.md) (`tenant_key` override axis for the RESO terminology corpus)
**Scope**: CDL project `ofzcokolkeejgqfjaszq` (`matrix-platform-foundation/supabase/cdl/`): new table `public.app_ui_strings`, new public read EF `app-i18n`, new `app_ui_string` write resource on `mls-sync`; FE pattern in `matrix-apps-template-2-1` and `matrix-pipeline-2-0`. **Does not touch SSO (`xgubaguglsnokjyudgvc`).**

## Context

Matrix apps shipped one bundled JSON file per locale (`en.json`, `ru.json`,
`hu.json`, …) compiled into the app. This made every translation a code change
and a redeploy, grew the bundle with each language, and could not be customised
per tenant at runtime. ADR-020 already moved RESO **terminology** (field /
resource / lookup nouns + the curated `App.*` glossary) into the CDL with a
`tenant_key` override axis served by `reso-dd-descriptions`. The remaining bulk
— generic UI **chrome** (`common` / `nav` / `settings` / `auth` / `sidebar` /
`reso.*` UI strings) — was still hand-maintained JSON.

The product goal is a Booking.com-style multi-language system: add a language by
adding data, translate any string from an admin surface, and never ship a large
per-locale bundle. This must be the **platform standard**, not a one-app feature.

## Decision

**Make every non-English UI string (and every per-tenant relabel of any locale,
including English) runtime data in the CDL. Keep exactly one bundled English
baseline per app as the offline / first-paint fallback. Serve locale bundles
from a public CDL EF behind a chained i18next backend, and manage everything
from the existing Translations & Labels admin tab.**

### 1. Storage (CDL `ofzcokolkeejgqfjaszq`) — `app_ui_strings`
- `app_ui_strings(app_key, namespace, string_key, locale, tenant_key text NOT NULL DEFAULT '', value, description, source DEFAULT 'app_default', created_at, updated_at)`, PK `(app_key, namespace, string_key, locale, tenant_key)`, index on `(app_key, locale, tenant_key)` + partial index `WHERE tenant_key <> ''`.
- `tenant_key = ''` is the **global app default**; a tenant UUID is that tenant's
  override (`source='team_override'`). `app_key` keeps each app's chrome separate;
  the RESO corpus (ADR-020) stays shared/global.
- `namespace` = the top-level i18n group (`common`/`settings`/`reso`/…) used only
  for admin grouping; `string_key` is the remaining dotted path. i18next
  interpolation (`{{role}}`) and plural suffixes (`_one`/`_other`) are preserved
  verbatim as distinct `string_key`s.
- RLS: UI text is non-sensitive → public/authenticated `SELECT`; **all writes via
  the EF** (no INSERT/UPDATE/DELETE policy), mirroring ADR-020.

### 2. Read EF `app-i18n` (new, `verify_jwt:false`, public read)
- `GET ?app=<app_key>&locale=<lng>[&tenant=<id>][&v=<ver>]` → a nested i18next
  resource tree `{ [namespace]: { [string_key]: value } }` for that locale.
- Per-key overlay: **global `<locale>` → tenant `<locale>`** (empty override =
  fall through). Global responses are CDN-cacheable with a versioned ETag; tenant
  responses are `private, no-store` so a relabel is visible immediately.

### 3. Write resource `app_ui_string` on `mls-sync`
- `list-resource` (global + this tenant's override side by side, with
  `app/locale/namespace/q/page/pageSize`), `upsert-resource` (single- or
  multi-locale `locales:{en,ru,…}`; empty value clears), `delete-resource`. The
  EF force-injects `tenant_key = caller.tenantId` + `source='team_override'`,
  scope-gates on the SSO claim (`global`/`org_admin`/`system_admin`), and emits
  `HistoryTransactional` (`ResourceName=AppUiString`).

### 4. FE runtime (chained i18next backend) — platform standard
- The app bundles **only** `locales/en.json`. `i18next` boots with
  `resources:{ en }`, `partialBundledLanguages:true`, `fallbackLng:'en'`.
- Backend chain: `LocalStorageBackend` (instant repeat paint, busted by a corpus
  `version`) → `HttpBackend` whose `loadPath` targets the CDL `app-i18n` EF with
  `app`, `{{lng}}`, the active `tenant`, and `version`.
- Tenant id is unknown at module load (i18n boots before auth); it is injected
  post-login via `setI18nTenant(tenantId)` from `AuthContext`, which purges the
  localStorage cache on tenant change (no cross-tenant bleed) and reloads the
  active locales. `reloadI18n(locales)` re-fetches after an admin edit.
- Adding a language = add the code to `SUPPORTED_LANGUAGES` + seed CDL rows. No
  new bundle. `APP_KEY` identifies the app's corpus.

### 5. Admin surface
- Settings → **Translations & Labels** gains an **"Interface text"** scope over
  `app_ui_string` (alongside the existing "Terminology" scope over the RESO
  corpus), a full pager (total, page X of N, first/prev/next/last, page-size),
  and an add-locale picker. Saving Interface text calls `reloadI18n()`; saving
  Terminology invalidates the `reso-dd-descriptions` cache — both flip live.

### 6. Authorization
- Same model as ADR-020: the FE hides the editor for non-admins; the CDL
  `mls-sync` EF re-checks the SSO scope claim before writing. No new SSO
  permission-catalog keys (apps authorise via `role_configurations` + scope).

## Consequences

- **Positive**: one store + one EF per app for all chrome; languages and
  per-tenant relabels are data, not deploys; bundle shrinks to a single English
  baseline; resilient (offline/EF-down degrades to English, never blank);
  consistent with ADR-020 (`tenant_key` axis, same write EF, same audit trail);
  baked into `matrix-apps-template-2-1` so every new app inherits it.
- **Negative / cost**: a non-English tenant's first paint may flash English until
  the CDL bundle hydrates (mitigated by the localStorage cache + Suspense); tenant
  responses are uncacheable at the CDN (mitigated by `version` + localStorage);
  the admin list editor fans out one `list-resource` per active locale.
- **Boundary**: every artifact lives in the **CDL** project. SSO only mints the
  JWT + scope claim the CDL EF verifies. No translation data in SSO.

## Alternatives considered

- **Keep bundled per-locale JSON** — rejected: every translation is a code change,
  the bundle grows per language, and no per-tenant customisation at runtime.
- **No bundled baseline (bootstrap-only stub from CDL)** — rejected: a slow/down
  EF or offline client would render blank; a single bundled English baseline is
  the resilient floor.
- **Separate per-app i18n table on each app DB (`wckwfbbqiupvallmhqbu`, …)** —
  rejected: splits translation truth across projects, can't share the RESO corpus,
  and duplicates the read/merge EF per app. `app_key` on one CDL table gives the
  same isolation without the sprawl.
- **Fold chrome into ADR-020's `reso_field_descriptions`** — rejected: that corpus
  is RESO-keyed (`field`/`lookup`) and shared globally; generic chrome is app-keyed
  and conceptually distinct, so a sibling table (`app_ui_strings`) keeps both clean.
