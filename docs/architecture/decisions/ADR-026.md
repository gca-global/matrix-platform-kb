# ADR-026: Event-sourced transaction model on canonical homes; Pipeline owns the Property transaction phase

**Status**: Accepted
**Date**: 2026-06-08
**Deciders**: Platform team (CDL owners) + Pipeline team
**Related**: [ADR-025](ADR-025.md) (Referral/Document project-flavour resources; offer-economics deferral — this ADR supersedes its "Property is Atlas-owned / read-only to this app" framing and un-defers the transaction-phase Property write-path), [ADR-016](ADR-016.md) (`cdl-write`/`cdl-read` dispatchers), [ADR-022](ADR-022.md) (`x_contact_key`), [ADR-023](ADR-023.md) (`x_` prefix), [ADR-012](ADR-012.md) (CDL split / no app service-role key), [data-distribution-and-stewardship.md](../data-distribution-and-stewardship.md) (process-based ownership + listing lifecycle state machine), [transaction-lifecycle.md](../../business-processes/canonical-processes/processes/transaction-lifecycle.md), [cdl-schema.md](../../data-models/cdl-schema.md)

## Context

`matrix-pipeline` 2.0 needs the transaction to *see* its buyer and its property and to drive the listing from offer to close. ADR-025 deferred the whole "offer" workstream and described the canonical close-side fields as living on an **Atlas-owned, read-only-to-this-app** `Property`. Two things forced a revisit:

1. **Ownership is by process, not by table.** Per `data-distribution-and-stewardship.md`, Atlas and Pipeline are both *thin clients* over the shared CDL. `Property` is a **shared** resource: Atlas owns the listing-creation / marketing phase; **Pipeline owns the transaction phase** (offer accepted -> under contract -> closed) and the canonical close economics. "Atlas-owned / read-only" was wrong — the correct model is a *governed transaction-phase write-path* for Pipeline.

2. **`TransactionManagement` has no canonical links.** In RESO DD it is a bare 4-field header (`TransactionKey`, `TransactionId`, `TransactionType`, `ModificationTimestamp`) with **zero foreign keys** — it cannot carry a buyer or a property link canonically. The buyer is a `Contact`; the canonical Contact<->Property junction is `ContactListings`. The cross-resource event/audit spine is `HistoryTransactional`.

A schema audit of the **live** CDL (`ofzcokolkeejgqfjaszq`) also corrected several stale assumptions in the KB:

- `public.properties` keys the RESO `ListingKey` on **`originating_system_key`** (not `listing_key`); currency is **`currency_code`**; there is **no** `lifecycle_state`, `locked_fields`, or `source_id` column. Field-level locks moved (migration `pr6`, `20260514100000`) to the **`property_field_overrides`** table behind the `cdl_lock_field` / `cdl_unlock_field` RPCs + `_cdl_property_field_is_locked()`.
- The canonical close/contract economics (`ClosePrice`, `CloseDate`, `PurchaseContractDate`, `ContractStatusChangeDate`) were **defined by RESO but never materialized** as columns.
- Live `properties.originating_system_name` carries a **tenant id** (`tenant-…`), not an `mls_sources` slug, so per-row source classification (matrix-internal vs qobrix/dash) is not yet resolvable from the data.

## Decision

Model the transaction **event-sourced on canonical homes**. Current-state facts live where RESO puts them; the timeline is the event spine. No structural columns are invented on `transaction_management`.

1. **Buyer <-> Property = `ContactListings`.** The buyer is a `Contact`; the link to the listing is a `ContactListings` row (`contact_key` + `listing_key`). No `x_contact_key` is added to `transaction_management`. `x_contact_key` (ADR-022) remains the generic "this process row is about this buyer Contact" extension for resources that genuinely have no canonical junction (showings); the transaction does have one (`ContactListings`), so it uses it.

2. **`Property` is the transaction subject and gains the missing canonical close economics.** Migration `20260608150000` adds `close_price`, `close_date`, `purchase_contract_date`, `contract_status_change_date` to `public.properties` (+ `properties_published` mirror) as canonical snake_case columns.

3. **`TransactionManagement` stays the bare canonical RESO header** — unchanged, no link columns.

4. **`HistoryTransactional` is the event spine.** Each transaction-phase transition is an append-only event anchored polymorphically on the Property (`ResourceName='Property'`, `ResourceRecordKey=ListingKey`, per the resource-coverage table in transaction-lifecycle.md), with `ChangeType` (`Under Contract` / `Closed` / `Back On Market`), `PreviousValue`/`NewValue` on `StandardStatus`, `ChangedByMemberKey`, and the buyer `contact_key` + `transaction_key` carried in `raw`. The buyer-of-record is therefore derivable from the spine canonically.

5. **Pipeline drives the transaction phase through a governed EF: `cdl-listing-lifecycle`.** Actions `acceptOffer` / `closeDeal` / `cancelDeal`:
   - validate the from->to `StandardStatus` transition and the caller's scope (`closeDeal`/`cancelDeal` require `org_admin`/`system_admin`; `acceptOffer` any broker scope),
   - update `Property` (`standard_status` Active->Pending->Closed projection; close economics),
   - auto-lock escrow fields (`list_price`, `bedrooms_total`, `bathrooms_total_integer`, `living_area`) via `cdl_lock_field` on `acceptOffer`, released via `cdl_unlock_field` on `cancelDeal`,
   - append a `property_lifecycle_events` audit row, confirm the buyer `ContactListings` row, and emit the `HistoryTransactional` event.
   `verify_jwt=false` with custom SSO-JWT verification; service-role inside; Pipeline never holds the CDL service-role key (ADR-012).

6. **Timeline read = `cdl-read` resource `history_transactional`.** Broker-scope, service-role-inside read anchored by `resource_name` + `resource_record_key`, returning full rows (incl. `new_value`/`raw`). The anon PII restriction in the app's `useContactHistory` (no `new_value` over the anon client) is unchanged; the full timeline read is EF-mediated.

7. **Source-of-record guard is wired but currently a no-op.** The EF resolves the property's source via `mls_sources.slug = properties.originating_system_name`; a non-internal source (`qobrix`/`dash`) puts the EF in **record-only** mode (sets economics + locks + events, does NOT flip the channel-facing `standard_status`). Because live properties carry a tenant id rather than a source slug, nothing resolves today and every row is drivable. The guard activates once per-row source classification lands.

## KB divergence

The KB previously described `properties.locked_fields` (jsonb) + `lifecycle_state` and a `listing_key` column. The **live schema diverged** (pr6 dropped the jsonb locks for `property_field_overrides`; `ListingKey` is stored as `originating_system_key`; no `lifecycle_state` column). This ADR records the live reality; the affected docs (`data-distribution-and-stewardship.md`, `cdl-schema.md`) are updated in the same change. The source-of-record guard diverges from the doc's "matrix-internal drives" rule only in that it is currently inert (no resolvable per-row source) — documented above, to be revisited when classification lands.

## Consequences

### Positive
- 100% canonical: `TransactionManagement` stays the exact RESO 4-field header; the buyer uses the canonical `ContactListings` junction; close economics use canonical `Property` fields; the timeline uses the canonical `HistoryTransactional` spine.
- Pipeline gets a governed, audited, lock-honoring transaction-phase write-path without holding a service-role key and without a second authz path.
- The buyer-of-record and transaction context are reconstructable from the event spine; no schema change is needed to add offer/transaction documents later (ADR-025 `document.related_resource`/`related_key`).

### Negative / notes
- In-flight offer *negotiation* economics (amount/currency/counter lifecycle before acceptance) remain deferred (ADR-025) — `cdl-listing-lifecycle` starts at `acceptOffer`.
- `HistoryTransactional.entity_event_sequence` ordering for these Pipeline-authored events relies on the existing sequencing; consumers should sort by `(resource_name, resource_record_key, entity_event_sequence)` where available.
- The source-of-record guard is inert until properties carry a resolvable source slug.

## Alternatives considered
- **Add `listing_key`/`x_contact_key` columns to `transaction_management`** — rejected: invents non-canonical foreign keys on a RESO-bare header; the canonical homes (`ContactListings`, `Property`, `HistoryTransactional`) already express every relationship.
- **Extend `cdl-write` to `properties` instead of a lifecycle EF** — rejected: the transaction phase is a guarded state machine (transition + scope validation, escrow locks, lifecycle audit), not a generic column write; a dedicated EF keeps the state machine in one governed place.
- **Keep "Property read-only to Pipeline" (ADR-025 framing)** — rejected: contradicts the process-based ownership model; Pipeline legitimately owns the transaction phase of the shared Property.
