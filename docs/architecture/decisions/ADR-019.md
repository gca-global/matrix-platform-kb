# ADR-019: Server-managed PKCE for first-party public clients (webview-proof login)

**Status**: Accepted
**Date**: 2026-05-31
**Extends**: [ADR-011](ADR-011.md) (ES256 signing), [ADR-017](ADR-017.md) (token storage / BFF direction), [ADR-018](ADR-018.md) (issuer URL + TPA)

## Context

Matrix Apps are public OAuth clients that authenticate with **OAuth 2.1 +
PKCE**. The client generates a `code_verifier`, derives a `code_challenge`,
stores the verifier in browser storage, redirects to the SSO/Microsoft login,
and on callback exchanges `code + code_verifier` for tokens.

A **fresh login** is the *only* flow that requires the client to carry a secret
(the `code_verifier`) across the cross-origin `app → microsoftonline.com → app`
redirect. The Cursor in-IDE browser is a sandboxed Electron webview that **drops
both `sessionStorage` AND `localStorage` across that hop** (proven: the deployed
build already mirrored the verifier to `localStorage` and still threw
`missing_pkce_state`). The `code` and `state` survive only because they arrive in
the **callback URL**, not in storage.

This was latent for a long time: a previously-cached token let the app skip the
fresh-login path entirely. The [ADR-011](ADR-011.md) ES256 *fail-closed* fix plus
the [ADR-018](ADR-018.md) issuer change **invalidated those cached tokens**,
forcing the fresh-login path the webview cannot complete — surfacing as an SSO
redirect loop in Cursor. Real browsers were never affected (same-origin storage
survives the round-trip).

Cursor exposes **no storage/cookie configuration knob** for its webview, so a
client-storage-based fix is impossible there.

## Decision

**Let opted-in first-party public clients use server-managed PKCE: the SSO
authorizes the code→token exchange without a client-presented `code_verifier`.**

- New column `sso_applications.server_managed_pkce boolean not null default
  false`. Opt-in **per app**; pilot client is Matrix Pipeline 2.0
  (`e2b4f0fa-8adb-4ffb-8c08-c49c46307ddd`).
- `oauth-token` requires `code_verifier` for a public client **only when
  `!app.server_managed_pkce`**. The existing challenge-validation block stays
  conditional on `authCode.code_challenge`, so when an opted-in client sends no
  challenge, nothing validates a verifier. All other protections are unchanged.
- The opted-in client sends **no `code_challenge` and no `code_verifier`**, does
  **not** persist a verifier/state, and exchanges on the **code alone**. A
  `state` is still generated and passed for SSO-side correlation. Tokens are
  stored only **after** the redirect completes (same-origin, persists).

```
App login (no verifier, no challenge)
  → SSO authorize + Microsoft
  → callback URL carries code + state (survives the webview)
  → exchangeCodeForToken(code)  [CORS fetch, no verifier]
  → oauth-token: server_managed_pkce app → issue tokens
  → store tokens in localStorage (same-origin, persists)
```

## Security posture

Server-managed PKCE trades **client-side PKCE code-interception protection** and
**client-side CSRF `state` validation** for the protections that remain on the
server:

- authorization codes are **single-use** (burned on exchange),
- **short TTL** (10 min; consider tightening),
- **strict `redirect_uri` allowlist match** (`authCode.redirect_uri === redirect_uri`),
- **`client_id` binding** — `oauth-token` rejects a code whose stored `client_id`
  ≠ the requesting `client_id` (enforced 2026-06-01; previously asserted in the KB
  but not implemented — a spec/impl drift closed as part of this hardening),
- a **valid, authenticated SSO session** behind the authorize step.

**CSRF `state` — accepted residual risk (no sound server-side equivalent).** A
real `state` CSRF defense requires the client to compare the callback `state`
against a value it stored *before* the redirect. In server-managed mode the client
holds no such secret — only the URL-supplied `state`, which an attacker controls in
a code-injection scenario — and re-introducing client-stored `state` would
reintroduce the exact storage-loss failure this ADR exists to avoid. A server-side
"verify the URL `state`" check would therefore be a placebo and is deliberately
**not** added. We **accept** the residual login-CSRF/code-injection risk for
first-party public clients, bounded by: single-use + short-TTL codes,
`redirect_uri`/`client_id` binding, an authenticated SSO session at authorize, the
authorize-step app-access gate (the attacker must be an authorized SSO user), and a
first-party all-employee population. The durable fix is the [ADR-017](ADR-017.md)
BFF / HttpOnly-cookie direction; until then, non-webview clients MAY retain
client-side `state` validation.

This is the pragmatic **confidential-client / BFF posture** for *first-party*
apps and aligns with [ADR-017](ADR-017.md)'s direction. It is **not** a license
to disable PKCE broadly: the flag is per-app and intended for first-party public
clients only. Third-party or lower-trust clients MUST keep client-side PKCE
(default `false`).

## Bounded authorization-code replay window (2026-06-01)

**Problem.** Strict single-use codes break fresh login in embedded/preview
browsers that *reload* `/auth/callback` and **cancel** the in-flight document.
The Lovable preview rewrites the callback URL (`callback_lovable_sha=…` 302s) and
loads it in several short-lived documents; the **first** exchange consumes the
code server-side, but its HTTP response (the tokens) dies with the torn-down
fetch, so every later document re-presents the now-spent code and gets
`invalid_grant` → the user dead-ends on "the sign-in code expired". React
StrictMode double-invoke and link prefetch produce the same class of failure. A
purely client-side fix is impossible: tokens cannot be recovered from a fetch
whose JS context was destroyed.

**Decision.** `oauth-token` grants the `authorization_code` flow a **bounded,
same-client replay window** (`REPLAY_WINDOW_MS = 60_000`). On first consumption it
records `consumed_at` and caches the issued `access_token` + `refresh_token` on
the code row (migration `20260601210000_add_authcode_replay_window`). If the
**same** code is re-presented by the **same** `client_id` + `redirect_uri` within
the window, the server **re-delivers the identical tokens** (HTTP 200) instead of
`invalid_grant`. Outside the window — or once a cleanup nulls the cached tokens
(`sso_clear_expired_authcode_tokens()`, >2 min) — the code is fully spent.

**Why this is safe.**
- It returns the **same** access + refresh token issued the first time. It does
  **not** mint a new session and does **not** rotate the refresh token, so it
  adds **no new credential** and causes **no session multiplication**.
- **All** existing bindings are still enforced on the replay path: `client_id`,
  `redirect_uri`, code expiry, and PKCE (when a `code_challenge` is present).
- The relaxation of strict single-use is bounded to ≤60 s and is risk-equivalent
  to the code's own in-transit value extended by that window — accepted for
  first-party server-managed-PKCE public clients.
- Consumption now happens **after** a successful mint+persist (not before), so a
  transient signing/storage error leaves the code reusable instead of burning it.

**Client effect.** With server replay, the loser document's exchange returns 200
(cached tokens) and lands home on its own; `AuthCallback.tsx`'s
`waitForSiblingSession` remains a harmless fallback. No client change required.

## Consequences

### Positive
- Fresh login completes in storage-stripping embedded browsers (Cursor in-IDE
  browser) and in real browsers alike, with no client-storage dependency on the
  redirect hop.
- Backward compatible: an **old** Pipeline build still sends challenge+verifier
  and still validates fine (the challenge block remains conditional), so the
  server change can ship before the client change with no breakage window.
- No new secret distribution; nothing leaves the SSO project.

### Negative / accepted
- Loses client-side code-interception/CSRF defense for opted-in apps. The
  code-interception loss is covered by single-use + short-TTL + redirect_uri/
  client_id binding + an authenticated SSO session; the CSRF-`state` loss is an
  **explicitly accepted residual risk** (see Security posture) — there is no sound
  server-side `state` equivalent without a client-held secret.
- Per-app rollout: each app must set the flag **and** ship the client constant.

## Rollout

- [x] Migration: `sso_applications.server_managed_pkce` (default false); set
      `true` for the Pipeline client (2026-05-31).
- [x] `oauth-token` gate relaxed (`!app.server_managed_pkce`), redeployed with
      `verify_jwt: false` (2026-05-31). Live gate test confirmed: Pipeline
      without a verifier reaches `invalid_grant` (gate passed); Atlas MLS without
      a verifier still returns `code_verifier is required` (unchanged).
- [x] Pipeline client (`matrix-sso.ts` + `AuthCallback.tsx`) shipped behind
      `SERVER_MANAGED_PKCE = true`; deployed via github-watcher (2026-05-31).
- [x] **`client_id` binding enforced** in `oauth-token` and redeployed with
      `verify_jwt: false` (2026-06-01) — closes cross-client code replay.
- [x] **Callback single-use reorder** (`AuthCallback.tsx`, 2026-06-01): join the
      in-flight exchange before any burn check; remove the pre-flight burn; burn
      only on a terminal outcome. Fixes the false "this sign-in link has already
      been used" error on benign React remounts (the SSO server's single-use
      enforcement remains authoritative).
- [x] **Entra tenant posture confirmed single-tenant** (2026-06-01): all 56 Azure
      identities in the SSO project share one tenant issuer
      (`login.microsoftonline.com/2ae67cc3-…/v2.0`), so the multi-tenant
      unverified-email (`xms_edov`) impersonation vector does not apply; email from
      the broker is trustworthy without an `xms_edov` check. Revisit if the Azure
      app is ever reconfigured multi-tenant (`common`/`organizations`).
- [x] **Bounded authorization-code replay window** (2026-06-01): migration
      `20260601210000_add_authcode_replay_window` (adds `consumed_at`,
      `issued_access_token`, `issued_refresh_token` + `sso_clear_expired_authcode_tokens()`);
      `oauth-token` redeployed with `verify_jwt: false`. Live test confirmed: two
      immediate POSTs of one code return **identical** tokens (200/200); the same
      code aged >60 s returns `invalid_grant`; a mismatched client is still
      rejected. Fixes the Lovable-preview fresh-login loop.
- [ ] Interactive fresh-login confirmation in the Cursor in-IDE browser AND a
      real browser (requires a real user sign-in).
- [ ] Roll out per app later: set the flag + ship each app's client constant and
      the apps-template default.
