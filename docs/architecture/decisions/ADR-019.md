# ADR-019: Server-managed PKCE for first-party public clients (webview-proof login)

**Status**: Accepted
**Date**: 2026-05-31
**Extends**: [ADR-011](ADR-011.md) (ES256 signing), [ADR-017](ADR-017.md) (token storage / BFF direction), [ADR-018](ADR-018.md) (issuer URL + TPA)

## Context

Matrix Apps are public OAuth clients that authenticate with **OAuth 2.1 +
PKCE**. The client generates a `code_verifier`, derives a `code_challenge`,
stores the verifier in browser storage, redirects to the SSO/Microsoft login,
and on callback exchanges `code + code_verifier` for tokens.

A **fresh login** is the *only* flow that requires the client to carry a secret
(the `code_verifier`) across the cross-origin `app → microsoftonline.com → app`
redirect. The Cursor in-IDE browser is a sandboxed Electron webview that **drops
both `sessionStorage` AND `localStorage` across that hop** (proven: the deployed
build already mirrored the verifier to `localStorage` and still threw
`missing_pkce_state`). The `code` and `state` survive only because they arrive in
the **callback URL**, not in storage.

This was latent for a long time: a previously-cached token let the app skip the
fresh-login path entirely. The [ADR-011](ADR-011.md) ES256 *fail-closed* fix plus
the [ADR-018](ADR-018.md) issuer change **invalidated those cached tokens**,
forcing the fresh-login path the webview cannot complete — surfacing as an SSO
redirect loop in Cursor. Real browsers were never affected (same-origin storage
survives the round-trip).

Cursor exposes **no storage/cookie configuration knob** for its webview, so a
client-storage-based fix is impossible there.

## Decision

**Let opted-in first-party public clients use server-managed PKCE: the SSO
authorizes the code→token exchange without a client-presented `code_verifier`.**

- New column `sso_applications.server_managed_pkce boolean not null default
  false`. Opt-in **per app**; pilot client is Matrix Pipeline 2.0
  (`e2b4f0fa-8adb-4ffb-8c08-c49c46307ddd`).
- `oauth-token` requires `code_verifier` for a public client **only when
  `!app.server_managed_pkce`**. The existing challenge-validation block stays
  conditional on `authCode.code_challenge`, so when an opted-in client sends no
  challenge, nothing validates a verifier. All other protections are unchanged.
- The opted-in client sends **no `code_challenge` and no `code_verifier`**, does
  **not** persist a verifier/state, and exchanges on the **code alone**. A
  `state` is still generated and passed for SSO-side correlation. Tokens are
  stored only **after** the redirect completes (same-origin, persists).

```
App login (no verifier, no challenge)
  → SSO authorize + Microsoft
  → callback URL carries code + state (survives the webview)
  → exchangeCodeForToken(code)  [CORS fetch, no verifier]
  → oauth-token: server_managed_pkce app → issue tokens
  → store tokens in localStorage (same-origin, persists)
```

## Security posture

Server-managed PKCE trades **client-side PKCE code-interception protection** and
**client-side CSRF `state` validation** for the protections that remain on the
server:

- authorization codes are **single-use** (burned on exchange),
- **short TTL** (10 min; consider tightening),
- **strict `redirect_uri` allowlist match** (`authCode.redirect_uri === redirect_uri`),
- **`client_id` binding**,
- a **valid, authenticated SSO session** behind the authorize step.

This is the pragmatic **confidential-client / BFF posture** for *first-party*
apps and aligns with [ADR-017](ADR-017.md)'s direction. It is **not** a license
to disable PKCE broadly: the flag is per-app and intended for first-party public
clients only. Third-party or lower-trust clients MUST keep client-side PKCE
(default `false`).

## Consequences

### Positive
- Fresh login completes in storage-stripping embedded browsers (Cursor in-IDE
  browser) and in real browsers alike, with no client-storage dependency on the
  redirect hop.
- Backward compatible: an **old** Pipeline build still sends challenge+verifier
  and still validates fine (the challenge block remains conditional), so the
  server change can ship before the client change with no breakage window.
- No new secret distribution; nothing leaves the SSO project.

### Negative / accepted
- Loses client-side code-interception/CSRF defense for opted-in apps (mitigated
  by single-use + short-TTL + redirect_uri/client_id binding + SSO session).
- Per-app rollout: each app must set the flag **and** ship the client constant.

## Rollout

- [x] Migration: `sso_applications.server_managed_pkce` (default false); set
      `true` for the Pipeline client (2026-05-31).
- [x] `oauth-token` gate relaxed (`!app.server_managed_pkce`), redeployed with
      `verify_jwt: false` (2026-05-31). Live gate test confirmed: Pipeline
      without a verifier reaches `invalid_grant` (gate passed); Atlas MLS without
      a verifier still returns `code_verifier is required` (unchanged).
- [x] Pipeline client (`matrix-sso.ts` + `AuthCallback.tsx`) shipped behind
      `SERVER_MANAGED_PKCE = true`; deployed via github-watcher (2026-05-31).
- [ ] Interactive fresh-login confirmation in the Cursor in-IDE browser AND a
      real browser (requires a real user sign-in).
- [ ] Roll out per app later: set the flag + ship each app's client constant and
      the apps-template default.
