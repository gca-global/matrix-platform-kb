# ADR-023: Platform extension prefix `x_` (supersedes `x_sm_`)

**Status**: Accepted
**Date**: 2026-06-05
**Deciders**: Platform team (CDL owners) + Pipeline team (matrix-pipeline 2.0)
**Related**: [ADR-022](ADR-022.md) (buyer-to-showing extension), [ADR-014](ADR-014.md) (ingestion provenance), [platform-extensions.md](../../data-models/platform-extensions.md) (extension governance)

## Context

Sharp Matrix stores a small number of fields that have **no RESO DD 2.0 equivalent**
as platform extension columns. These were originally tagged with a vendor prefix
`x_sm_` ("Sharp Matrix"), governed in
[`platform-extensions.md`](../../data-models/platform-extensions.md) and enforced
by the source-mapping gate `source-mappings/scripts/04_join_alignment.py`
(GATE 1: an `is_extension=true` field must start with the extension prefix).

Two things made the `x_sm_` prefix worth revisiting:

- **It had already drifted to `x_` in practice.** The 2026-05 extension-column
  audit (`matrix-platform-foundation/supabase/cdl/docs/2026-05-extension-columns-audit.md`)
  recommends a bare `x_` prefix for every newly classified extension
  (`x_is_visible`, `x_title_en`, `x_lead_source`, `x_slug`, …) and explicitly
  labels the existing `x_sm_*` columns as "already correctly `x_`-prefixed".
  The codebase was carrying two spellings of the same idea.
- **The vendor tag adds no value.** Extension columns are never emitted to
  outbound RESO / Anywhere Dash channels (they are local-only), so the `_sm_`
  vendor segment communicates nothing a generic local-field marker doesn't.

## Decision

Adopt **`x_`** as the single platform extension prefix. `x_sm_` is retired.

- The governed convention in [`platform-extensions.md`](../../data-models/platform-extensions.md)
  is now `x_`; the gate `04_join_alignment.py` requires extension fields to
  start with `x_`.
- The four **materialized** extension columns were renamed in lockstep by CDL
  migration `20260605160000_rename_x_sm_extensions_to_x.sql`
  (`ALTER ... RENAME COLUMN`, data-preserving):
  - `public.contacts.x_sm_privacy_level` → `x_privacy_level`
  - `public.showings.x_sm_contact_key` → `x_contact_key`
  - `public.showing.x_sm_contact_key` → `x_contact_key`
  - `public.showing_request.x_sm_contact_key` → `x_contact_key`
  - plus the three `idx_*_x_sm_contact_key` indexes → `idx_*_x_contact_key`.
- The breaking surface (app reads/writes these column names via `cdl-write` /
  `cdl-read`) was shipped lockstep: `cdl-read`'s filterable allow-lists and the
  matrix-pipeline app (`useShowingChain`, `EngagementTimeline`, `Showings`,
  `contactsSchema`) were updated to `x_contact_key` / `x_privacy_level` in the
  same change.
- All KB references to `x_sm_*` (governance, source-mappings catalogue + curated
  CSV + generated wiki docs, ADRs, process docs, vision) were normalized to
  `x_`. Spec-only extension entries (the ingestion provenance family in ADR-014,
  SIR brand markers, etc.) are doc-level only — none were materialized as
  `x_sm_` columns (verified against `information_schema` 2026-06-05).

## RESO divergence (KB-first escape hatch)

RESO DD 2.0 defines **no** extension prefix at all — neither `x_sm_` nor `x_`.
The `x_` prefix is therefore a **deliberate Sharp Matrix platform convention**, a
local-field marker with no RESO basis. This is a conscious divergence recorded
here per the kb-first rule's escape hatch:

- **Diverges from:** RESO DD 2.0 (which has no extension-naming standard) and the
  prior governed `x_sm_` standard in `platform-extensions.md`.
- **Reason:** consolidate on the prefix the codebase had already adopted, drop a
  vendor tag that carries no information for local-only columns.
- **KB updated in the same change:** `platform-extensions.md` and the gate script
  now define `x_` as the standard, so this is the governed convention — not a
  silent divergence.
- **Invariant preserved:** `x_` columns are local-only and MUST NOT be emitted to
  outbound RESO / Dash channels. If a future RESO DD version adds a matching
  field, migrate the extension to the RESO name per the platform-extensions
  retirement rule.

## Consequences

### Positive
- One prefix, one governance rule, one gate — no more `x_sm_` / `x_` ambiguity.
- Cheaper, clearer column names; the rename was data-preserving.

### Negative / notes
- Breaking rename of four live columns; required lockstep CDL + EF + app deploy
  (done). Applied historical migrations keep their original `x_sm_` text
  (append-only); this migration + ADR document the change.
- Any future inbound mapping or EF that hard-codes `x_sm_` must use `x_`.

## Alternatives considered
- **Keep `x_sm_`** — rejected: the audit + new columns had already standardized
  on `x_`, leaving two spellings of one convention.
- **Drop the columns / move to `raw` jsonb** — rejected: the four columns back
  shipped features (buyer-to-showing linkage, contact privacy) and need to be
  typed, indexed, and filterable.
