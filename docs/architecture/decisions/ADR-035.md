# ADR-035: Opportunity lives in the Pipeline App DB (not the CDL), stage still calculated

**Status**: Accepted
**Date**: 2026-06-18
**Deciders**: Pipeline team (matrix-pipeline 2.0) + platform team (CDL owners)
**Supersedes**: [ADR-034](ADR-034.md) (Opportunity as a stored CDL super-resource)
**Related**: [ADR-029](ADR-029.md) (stage-as-projection), [ADR-012](ADR-012.md)/[ADR-013](ADR-013.md)/[ADR-014](ADR-014.md) (CDL split, no app service-role key), [ADR-016](ADR-016.md) (`cdl-write` dispatcher), [app-template.md](../../platform/app-template.md) (dual-Supabase, Pattern B SSO-claim RLS), [opportunity-model.md](../../data-models/opportunity-model.md), [matrix-pipeline architecture.md](../../product-specs/matrix-pipeline/wiki/architecture.md)

## Context

[ADR-034](ADR-034.md) (accepted 2026-06-17) introduced a stored `opportunity` +
`opportunity_link` super-resource and placed it in the **CDL**
(`ofzcokolkeejgqfjaszq`), reasoning that the Opportunity is tightly coupled to the
RESO resources it aggregates and that co-location buys fast indexed joins.

One day of implementation surfaced two facts that invalidate the CDL placement:

1. **The link model is loose-key, app-resolved — there is no cross-project join.**
   ADR-034 D3 itself mandates that `opportunity_link` uses loose
   `(resource_name, resource_key)` text refs with **no foreign keys**, and the
   detail view resolves each sub-resource through its existing CDL read EF. So the
   app *never* issues a SQL join between `opportunity` and `contacts`/`saved_search`/
   etc. **The "co-located indexed join" benefit ADR-034 cited never materialises.**
   Whether `opportunity` sits in the CDL or the App DB, sub-resources are still
   resolved app-side via `cdl-read` — identical read pattern, identical latency.

2. **The Opportunity is app-private CRM workflow, and the CDL is change-controlled
   outside Lovable.** RESO DD 2.0 has no Opportunity/Deal. The matrix-pipeline KB
   already classifies the Pipeline-state funnel, `activities` (CRM workflow state),
   the commission engine, and app lookup tables as **App-DB-private**
   ([architecture.md](../../product-specs/matrix-pipeline/wiki/architecture.md)).
   CDL schema only changes through `matrix-platform-foundation` (not Lovable-managed),
   so keeping the sales-process model in the CDL **permanently blocks Lovable** from
   iterating on it and forces every column tweak through the platform change-control
   bottleneck.

`matrix-pipeline` is the CRM and the only foreseeable consumer of opportunities
(YAGNI for cross-app reuse).

## Decision

**Relocate `opportunity` + `opportunity_link` from the CDL into the Pipeline App DB
(`kzvhqgpedapzqmwgikrw`, Lovable-managed).** They become app-private CRM tables
alongside `activities` / `role_configurations` / the commission engine, read and
written **directly with the `supabase` app client under SSO-claim RLS** — no
`cdl-write`/`cdl-read` hop. The CDL tables (which held only test rows) are dropped
and both resources are de-registered from the CDL EFs.

### D1 — Home = App DB, access = direct PostgREST under SSO-claim RLS

`public.opportunity` + `public.opportunity_link` are created in the App DB by
`matrix-pipeline-2-0/supabase/migrations/20260618120000_opportunity_appdb.sql`
(Cursor-authored, committed so Lovable sees it as the schema source of truth).
RLS uses the 5-level scope **Pattern B** from `003_data_model_template.sql`
(`get_crud()` / `get_active_scope()` / `get_my_record_id_v2()` /
`get_current_tenant_id()`), mirroring `public.activities`. `owner_id` (SSO `sub`)
drives self/team scope; `owner_member_key` (the CDL member key) is retained for
display/assignment only. The app already sends the SSO ES256 JWT on every App-DB
PostgREST request (`src/integrations/supabase/client.ts`), so no new auth surface
is introduced and the app still holds **no CDL service-role key**
([ADR-013](ADR-013.md)).

### D2 — Stage is CALCULATED ONLY (carried forward from ADR-034 D2, unchanged)

There is still **no `stage` column**. The 5-stage funnel position is derived on
read by `deriveOpportunityStage()` (`src/lib/opportunityStage.ts`) from the linked
sub-resources' lifecycles. The [architecture.md](../../product-specs/matrix-pipeline/wiki/architecture.md)
"Pipeline gate" (no stored stage, no `pipeline_stages` table) is preserved.
`opportunity_status` (`open`/`won`/`lost`/`archived`) remains the anchor's
operational state, not the funnel stage.

### D3 — Linkage is loose `(resource_name, resource_key)` refs, no FK (carried forward from ADR-034 D3)

`opportunity_link` records `(opportunity_key, resource_name, resource_key, role)`
with **no foreign keys**. Sub-resources live in the CDL and are resolved app-side
via the CDL read EFs. The deterministic key
`<opportunity_key>:<resource_name>:<resource_key>` keeps linking idempotent. This
is unchanged from ADR-034 — and is precisely why CDL co-location bought nothing.

### D4 — `transaction_management` demotion is unchanged

ADR-034 D4 stands: the RESO `TransactionManagement` header is retained in the CDL
and linked from an opportunity via `opportunity_link (resource_name =
'TransactionManagement')`, not authored standalone. Unaffected by the move.

### D5 — CDL is cleanly reversed

The CDL `opportunity` + `opportunity_link` tables (2 + 2 test rows from the
ADR-034 validation round-trips, no production data) are dropped
(`matrix-platform-foundation/supabase/cdl/migrations/20260618130000_drop_opportunity_super_resource.sql`),
and both resources are de-registered from `cdl-write` (→ v15) and `cdl-read`
(→ v12) and redeployed. The CDL EF allow-lists no longer expose them.

## Consequences

### Positive
- **Lovable owns the sales-process schema** and can evolve it via App-DB
  migrations without the CDL change-control bottleneck.
- **Faster writes**: direct PostgREST under RLS removes the `cdl-write`/`cdl-read`
  EF hop; not bound by the CDL listings p99 contract. Tenant/owner/status indexes
  scale for many users × many opportunities.
- **No regression in reads**: sub-resources were always resolved app-side via EFs;
  that path is unchanged.
- Reuses the established App-DB Pattern B RLS (same as `activities`) — no new auth
  surface, no app service-role key.

### Negative / notes
- Opportunities are now **Pipeline-app-private** and not directly reusable by other
  Matrix apps. Accepted (YAGNI). If a second app ever needs them, promote to the
  CDL then.
- The stage is still a read-time projection (unchanged trade-off from ADR-029/034).
- `opportunity_link.resource_key` remains a loose witness (no FK); orphaning is
  surfaced in the UI, not enforced by the DB (same posture as ADR-033/034).

## Alternatives considered
- **Keep it in the CDL (ADR-034)**: rejected — co-located join benefit never
  materialises (loose-key, app-resolved links), and CDL change-control blocks
  Lovable from iterating on app-private CRM workflow.
- **Store the stage as a column**: rejected (unchanged from ADR-034) — re-introduces
  drift; violates the Pipeline gate.
