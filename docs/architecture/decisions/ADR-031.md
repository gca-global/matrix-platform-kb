# ADR-031: matrix-pipeline may provision a CDL Member from Active Directory via `cdl-write`

**Status**: Accepted
**Date**: 2026-06-15
**Deciders**: Platform team (CDL owners) + Pipeline team
**Related**: [ADR-012](ADR-012.md) (dedicated CDL project), [ADR-016](ADR-016.md) (`cdl-write` single dispatcher), [ADR-013](ADR-013.md) (no CDL service-role key in apps), [cdl-crud-contract.md](../../product-specs/matrix-pipeline/cdl-crud-contract.md), [cdl-schema.md](../../data-models/cdl-schema.md), [wiki/architecture.md#identity-boundary](../../product-specs/matrix-pipeline/wiki/architecture.md)

## Context

When a Pipeline broker creates a Contact, the owner picker (`OwnerEmployeePicker` → `useEnsureMemberFromAD`) lets them select the owning employee from the **Active Directory** roster (Azure AD, surfaced via the SSO `admin-ad-users` EF). The Contact's `owner_member_key` must be a canonical CDL `Member.MemberKey`. If the picked AD employee already has a `members` row matched by email, the existing `member_key` is reused. If not, the app must mint a new Member.

Two problems blocked this:

1. **`cdl-write` did not allow `members`.** Its static `RESOURCES` registry covered 16 resources; `members` was absent, so the provisioning call returned `400 unknown or non-writable resource 'members'` and blanked the screen.
2. **The CDL Member contract was "read-only consumer"** ([cdl-crud-contract.md](../../product-specs/matrix-pipeline/cdl-crud-contract.md)): the roster was master-sourced only by `mls-sync.run-side-resources` from RESO feeds (predominantly legacy Qobrix/Cyprus rows). The intended SSO-user ↔ Member mapping (via canonical `Member.MemberAlternateId`) was **never materialized** — `members` had no `member_alternate_id` column, so the only viable SSO↔roster join was `member_email`. This drift is recorded in [wiki/architecture.md#identity-boundary](../../product-specs/matrix-pipeline/wiki/architecture.md) and [cdl-schema.md](../../data-models/cdl-schema.md) ("Owner-clamp deferred"), and the `sso-member-roster-lint` EF exists only to report it.

The product decision is to treat **Active Directory as the source of truth for new owner/member identity**, so the app needs a first-class, governed way to create a Member at the moment of contact creation.

## Decision

Allow `matrix-pipeline` to **insert** CDL `Member` rows from Active Directory through the existing `cdl-write` dispatcher, and materialize the SSO↔roster mapping the KB always intended.

1. **Register `members` as a writable strict-RESO resource** in `cdl-write` (`matrix-platform-foundation/supabase/cdl/functions/cdl-write/index.ts`): `{ table: "members", keyColumn: "member_key", sourceKeyColumn: "originating_system_member_key", systemColumn: "originating_system_name", resourceName: "Member" }`. Same envelope as `contacts` — the EF mints `member_key` (UUID) when absent, mirrors it into `originating_system_member_key`, defaults `originating_system_name` to the Pipeline source slug, and stamps `modification_timestamp`. No soft-delete column, so `delete` is rejected (consistent with `contacts`).
2. **Add the canonical RESO `member_alternate_id`** (RESO DD 2.0 `MemberAlternateId`, String, max 50, Active) column to `public.members` — plain canonical snake_case, **not** an `x_` extension. For app-provisioned members it carries the **Azure AD object id** (immutable GUID), finally materializing the SSO `user_id` ↔ `Member.MemberKey` mapping.
3. **App payload is canonical.** `useEnsureMemberFromAD` sends RESO snake_case fields (`member_email`, `member_first_name/last_name/full_name`, `member_mobile_phone`, `job_title`, `member_status='Active'`, `member_type='Agent'`, `member_alternate_id=<azureObjectId>`). The previously-sent `source_system` / `source_record_id` (non-existent columns on the strict-RESO table) are removed.
4. **Insert-only for the app.** Pipeline only provisions (creates) Members; it does not edit/delete the canonical roster. The roster otherwise stays **master-sourced by `mls-sync`**. `mls-sync` continues to own bulk reconciliation; app-minted rows are keyed under `originating_system_name = 'matrix-pipeline'` and so are distinguishable from feed-sourced rows.
5. **No new service-role exposure.** Writes still flow through `cdl-write` (service-role *inside* the EF, SSO-JWT-scoped); the app never holds the CDL service-role key (ADR-013 preserved). A `HistoryTransactional` `Member/New` row is emitted on every provision.

This is a **deliberate, documented divergence** from the prior "Member is read-only for Pipeline" rule — recorded here and reflected in the contract/schema docs in the same change.

## Consequences

### Positive
- The new-contact owner flow works end-to-end with AD as the identity source; no "ask an admin to provision" dead-end.
- The SSO↔roster mapping is materialized via canonical `member_alternate_id` (Azure object id), upgrading the fragile email-only join. `sso-member-roster-lint` can bootstrap from it.
- Reuses the existing single dispatcher (ADR-016) and its scope/redaction/history contract — no new EF, no service-role key in the app.

### Negative / notes
- **Two authorship sources for `members`** now coexist (`mls-sync` feeds + app provisioning). They are separated by `originating_system_name`; reconciliation/dedupe across the two remains a platform-team concern.
- **De-dupe is client-side only.** `useEnsureMemberFromAD` checks the cached roster by email before inserting; a rapid double-submit could mint a duplicate. Acceptable residual; a server-side unique guard on `(originating_system_name, member_email)` for the `matrix-pipeline` source is a possible future hardening.
- **Broad write scope.** `cdl-write` allows all broker scopes (`self`…`system_admin`), so any broker creating a contact can provision. Intentional (the picker is used by regular brokers); revisit if abuse surfaces.
- One Member-write path now exists that is not `mls-sync`; RESO-purity audits should treat `member_alternate_id` as canonical (it is) and app-minted rows as first-class.

## Alternatives considered
- **Keep Pipeline read-only; block provisioning** (owner picker only selects existing members, "ask an admin"): rejected — defeats the product decision to use AD as the owner source and creates an operational dead-end mid-contact-creation.
- **Dedicated platform-owned provisioning EF** (`cdl-provision-member`) instead of opening `cdl-write`: rejected for now — more surface area for the same write; the `cdl-write` dispatcher already provides the scope/history/service-role contract. Can be revisited if Member provisioning grows beyond the owner-picker case.
- **Store the Azure id in an `x_` extension** instead of `member_alternate_id`: rejected — `MemberAlternateId` is a real canonical RESO DD 2.0 field for exactly this purpose, so an `x_` column would be non-canonical drift.
