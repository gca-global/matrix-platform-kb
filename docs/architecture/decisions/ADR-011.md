# ADR-011: ES256 JWT Signing — Migration from HS256

**Status**: Accepted (in progress)
**Date**: 2026-04-09
**Supersedes**: Partial — extends ADR-002 (dual-Supabase) and ADR-008 (5-level scope)

## Context

The Sharp Matrix SSO platform originally signed all custom JWTs with **HS256 (HMAC-SHA256)** — a symmetric algorithm where the same secret is used for both signing and verification. This created several issues:

1. **Supabase PostgREST rejection**: Supabase projects that migrated to ES256 as their default signing algorithm rejected HS256 custom tokens with `PGRST301: No suitable key or wrong key type`, unless a legacy HS256 key remained in "Previously used" status.

2. **Secret distribution**: The same JWT secret had to be stored in the SSO vault AND shared with every app's Supabase project. A single compromised secret exposes all token verification.

3. **Supabase direction**: Supabase moved to ES256 (ECDSA P-256) as the default signing algorithm for new projects. HS256 is a legacy path.

4. **Key rotation**: Symmetric key rotation requires coordinated secret changes across all services simultaneously. Asymmetric keys allow public key distribution without exposing the signing key.

## Decision

**Migrate all SSO JWT signing from HS256 to ES256 (ECDSA P-256).**

### Implementation

1. Generate an ES256 key pair (P-256 curve) and store the private key as a JWK in the SSO vault (`sso_es256_signing_key`).

2. Import the ES256 public key as a **standby key** in each Supabase project that needs to verify SSO tokens. PostgREST automatically trusts standby keys for verification.

3. Update `oauth-token` and `switch-role` Edge Functions to sign with ES256 when the key is available, with HS256 as a fallback.

4. During the transition period, use a hybrid strategy: sign ES256 for apps using the SSO PostgREST directly; sign HS256 for apps with their own Supabase projects (which may not yet have the ES256 key imported).

5. Progressively import the ES256 key to all app Supabase projects, then remove the HS256 gate.

6. Promote ES256 to "current" key in all projects and retire HS256 secrets.

### Signing Decision Logic (Edge Functions)

```
if app has jwt_secret_name (own Supabase project):
    sign with HS256 using app-specific secret     ← transitional (HS256 apps)
else if ES256 vault key available (cached, w/ retry):
    sign with ES256 using vault key                ← target state
else:
    return HTTP 503 temporarily_unavailable        ← fail closed (ES256 apps)
```

> **Update (2026-05-31): ES256-or-fail-closed + cached signing key.** The
> previous "else → sign HS256 with SSO `JWT_SECRET`" fallback was removed for
> ES256 apps. A transient `get_vault_secret` failure used to silently downgrade
> to an HS256 token that the app's ES256-only PostgREST rejects (post-login
> `401` storm on `role_configurations` / `notifications`). `oauth-token`,
> `switch-role`, and `switch-tenant` now (a) cache the ES256 key in module scope
> (10 min TTL + in-flight de-dup) and retry the vault read, and (b) **fail closed
> with `503`** for ES256 apps when the key is unresolvable, rather than mint a
> broken token. The HS256 branch for `jwt_secret_name` apps is unchanged. See
> [sso-edge-functions.md](../../platform/sso-edge-functions.md#oauth-token).

### Verification Order (all verifying SSO EFs)

```
1. ES256 via JWKS (public key) — canonical (createRemoteJWKSet → sso-jwks)
2. App HS256 (vault secret)    — legacy jwt_secret_name app tokens
3. SSO HS256 (JWT_SECRET env)  — legacy SSO tokens
4. Opaque token lookup         — sso_access_tokens (only where allowOpaque)
```

### Verification consolidation (2026-07-09) — one JWKS mechanism

**Decision: SSO tokens are VERIFIED against the public key only, via the SSO
JWKS. No Edge Function fetches the private `sso_es256_signing_key` to verify.**

Five verification variants had accreted for the *same* ES256 token — JWKS
(CDL/ITSM EFs, app-DB Third-Party Auth), "fetch private JWK, strip `d`, then
`jwtVerify`", "fetch private JWK and verify with the private key" (a **bug** —
see below), HS256, and the opaque `sso_access_tokens` lookup. This is the
N-ways-to-prove-one-thing anti-pattern.

All verifying SSO EFs now call a single shared helper
`supabase/sso/functions/_shared/verify-sso-jwt.ts` → `verifySsoJwt(token, {
supabase, allowOpaque })`, which tries **ES256 via `createRemoteJWKSet` against
the public `sso-jwks` endpoint** first, then the legacy HS256 fallbacks, then
(only when `allowOpaque`) the opaque DB lookup. Signing is unchanged: the
private vault key is used **only** by `oauth-token` / `switch-role` /
`switch-tenant` / `mint-delegated-token` for `.sign()`.

Refactored onto the helper: `resolve-users`, `sso-member-roster-lint`,
`admin-tenants`, `oauth-userinfo`, `switch-tenant`, `switch-role`,
`mint-delegated-token`, and `_shared/admin.ts` (inherited by `admin-apps`,
`admin-dashboard`, `admin-microsoft-auth`, `admin-privileges`, `admin-groups`,
`admin-ad-users`, `admin-permissions`).

> **Gotcha — never `importJWK(privateJwk)` for verification.** WebCrypto refuses
> to verify a signature with a private key (`CryptoKey … must be of type
> "public"`). `resolve-users`, `sso-member-roster-lint`, and
> `mint-delegated-token` imported the vault **private** JWK and called
> `jwtVerify` with it; the verify threw and silently fell through to an
> unverified `decodeJwt` (or opaque lookup) — accepting tokens without checking
> the signature. The fix is to verify against the **public** key served by
> `sso-jwks` (`createRemoteJWKSet`), never the vault private key.

**Minimal-auth-mechanism policy (one mechanism per concern):**

- ONE credential everywhere: the **SSO ES256 JWT** (`MatrixSSOStorage.getAccessToken()`).
- ONE Edge Function verification: `verifySsoJwt()` → SSO JWKS.
- ONE DB-read verification: the SSO JWT checked against the SSO JWKS by PostgREST
  (Third-Party Auth on app/CDL DBs; GoTrue standby key on the SSO DB).
- ONE SSO-data read path: direct authenticated `ssoClient` PostgREST read (e.g.
  the TenantSwitcher tenant roster) — **not** the `admin-tenants` EF.
- Client access primitives: `ssoClient`, `cdlClient`, `createAnonDataLayerClient()`, and one EF invoker (`invokeSso`/`invokeCdl`).

Legitimate, genuinely-different mechanisms retained (NOT duplicates): the
`oauth-token` `client_id`/`client_secret` + PKCE bootstrap; `mint-delegated-token`
`X-Delegation-Secret` (M2M); `qobrix-*` EF Qobrix session headers (different
upstream); the server-side service-role client; and ITSM MCP HMAC tokens.

## Goal State

All SSO JWTs signed with ES256. Zero HS256 signing in production. The HS256 verification path remains for a deprecation period to accept tokens issued before the migration.

## Consequences

### Positive

- **Supabase-native**: ES256 is Supabase's default, so custom SSO tokens are indistinguishable from native tokens at the PostgREST layer.
- **No secret sharing**: Only the public key is distributed to app projects. The private key never leaves the SSO vault.
- **Standard JWKS**: Future option to expose a `/.well-known/jwks.json` endpoint for third-party integrations.
- **Key rotation**: Can rotate by generating a new key pair and importing the public key as standby, with zero downtime.
- **Lovable compatible**: Lovable apps use the Supabase JS client which is algorithm-agnostic — it just passes the token string.

### Negative

- **Transition complexity**: During hybrid phase, some tokens are ES256 and some HS256 depending on the app. Edge Functions must handle both.
- **Key import**: Each app's Supabase project requires a manual key import via the Dashboard (Management API support for standby keys is limited).
- **Vault dependency**: ES256 signing requires the vault key. As of 2026-05-31 the key is cached (module scope, 10 min TTL) with a retried fetch, so a transient vault blip no longer affects warm instances. If the key is genuinely unresolvable, ES256 apps **fail closed (`503`)** rather than downgrade to HS256 (see the signing-logic update above). HS256 (`jwt_secret_name`) apps are unaffected.

### Neutral

- **RLS helpers are algorithm-agnostic**: PostgreSQL RLS functions read `current_setting('request.jwt.claims')` which contains the decoded JWT payload regardless of signing algorithm. No RLS changes needed.
- **No app code changes**: Frontend apps store and pass the token string. The signing algorithm is transparent to application code.

### HS256 retirement gate — apps still on `jwt_secret_name` (2026-07-09)

The HS256 (and opaque-lookup) branch in `verify-sso-jwt.ts` **must not be removed**
until every app below is either migrated to Third-Party Auth / ES256 (clear
`jwt_secret_name`) or formally retired. As of 2026-07-09 the following **active**
apps still sign HS256:

| App | `client_id` (prefix) | `jwt_secret_name` | Migration note |
|-----|----------------------|-------------------|----------------|
| Sharp Matrix Portal | `sharp-matrix-vm-sso-v2-…` | `jwt_secret_sso_console` | Portal reads SSO PostgREST directly; migrate the shared `sso_console` secret set together. |
| Management Console | `sso-console-…` | `jwt_secret_sso_console` | Same shared secret as Portal. |
| Appointment Reports (meeting-hub) | `matrix-meeting-hub-vm-sso-v1-…` | `jwt_secret_sso_console` | **Legacy — do not break.** Reads via legacy CDL helper functions. |
| New Client Registration (client-connect) | `matrix-client-connect-vm-sso-v1-…` | `jwt_secret_sso_console` | **Legacy — do not break.** Reads via legacy CDL helper functions. |
| Matrix Apps Template 1.0 | `zc79lyd…` | `jwt_secret_template` | Obsolete template; retire rather than migrate. |
| Matrix HRMS Sandbox 3.0 | `a7b4570e-…` | `jwt_secret_smhrms_sandbox` | TPA already provisioned on `wltuhltnwhudgkkdsvsr`; can clear `jwt_secret_name` after ES256-read verification. |

Because four of these share `jwt_secret_sso_console`, retiring HS256 requires
migrating Portal + Console + meeting-hub + client-connect as one cohort. Until
then the HS256 branch stays and `oauth-token` keeps signing HS256 for these
`client_id`s. Only after the cohort is migrated/retired do we delete the HS256 +
opaque branches, leaving JWKS as the sole verifier, then promote the ES256
standby key to "current" (H1).
