# ADR-036: Qobrix-vanilla-inside — internal naming traces to the Qobrix OpenAPI spec, all deviations are `x_` extensions, UI terminology is an app-local i18n label layer

**Status**: Accepted
**Date**: 2026-07-11
**Deciders**: Sharp SIR sales-automation team (`gca-ltd/matrix-sales-automation`, was matrix-qobrix-sales-automation-v1-0) + platform team
**Related**: [ADR-023](ADR-023.md) (platform extension prefix `x_`), [ADR-020](ADR-020.md) (per-tenant/per-locale label overrides), [ADR-021](ADR-021.md) (runtime DB-driven i18n), [app-template.md](../../platform/app-template.md)

## Context

`matrix-sales-automation` ("Starjet"; was `matrix-qobrix-sales-automation-v1-0`) is a lift-and-shift of a Qobrix
sales workflow onto the Sharp Matrix app template. Qobrix publishes a canonical
OpenAPI specification (`docs/document.yaml`, `openapi: 3.1.0`) that defines every
resource (`Contact`, `Opportunity`, `Offer`, `Contract`, `Call`, `Meeting`,
`Task`, `PropertyViewing`, …) and every field, type, and enum.

An audit found the app had drifted from that spec in two ways:

1. **Internal naming drift** — app-DB columns, edge-function request/response
   keys, and frontend identifiers had accumulated names with no trace to a Qobrix
   `resource.field` (e.g. `contacts.vip_level`, `opportunities.budget_min`,
   `opportunities.lifecycle_state`, a non-spec `offers.offer_status` value set).
2. **Terminology baked into the contract** — user-facing wording was partly
   inherited from an unrelated project's **RESO Data Dictionary** i18n corpus and
   partly hardcoded in JSX, mixing "what the data is" with "what the word says".

The app template's i18n was also pointed at the shared **CDL** `app_ui_strings`
corpus (ADR-021), coupling this app's labels to platform-managed data it does not
own.

## Decision

Adopt **Qobrix-vanilla-inside + label-layer localization**: the app's internal
structure is 100 % Qobrix-OpenAPI-compliant, every genuine deviation is an
explicit `x_` extension, and every user-visible word is delivered through an
app-local i18n label layer keyed to the Qobrix model.

### D1 — The Qobrix OpenAPI spec is the internal naming source of truth

Every internal identifier (DB column, EF key, frontend field name/type) MUST
trace to exactly one of:

1. a Qobrix `resource.field` in `docs/document.yaml`, or
2. an explicit **`x_`** extension (per [ADR-023](ADR-023.md)), or
3. a platform-infra allowlist column:
   `id, tenant_id, created_at, updated_at, created_by, owner_team_id,
   external_qobrix_id, qobrix_created_by, qobrix_sync_state,
   qobrix_last_synced_at, qobrix_last_error, raw_qobrix`.

The machine-checkable dictionary is generated from the spec by
`scripts/gen_qobrix_dictionary.mjs` → `src/i18n/qobrix-dictionary.json`
(155 resources, 9 core). This is regenerated (not hand-edited) whenever the spec
changes.

### D2 — Deviations are `x_` extensions, recorded in a registry

`docs/qobrix-vanilla/extension-registry.{json,md}` (generated by
`scripts/gen_extension_registry.mjs` from the dictionary + an audited column
snapshot) classifies every column as **vanilla / infra / extension** and records
a per-extension decision (`map` to a vanilla field, `rename` to `x_`, keep as an
app-only `x_` extension, `document` an app column on a merged/app table, or
`infra`).

**Two-tier extension model.** Extensions are handled by whether the table is a
single Qobrix resource:

- **Single-resource tables** (`contacts` → Contact, `opportunities` →
  Opportunity): non-vanilla columns are **physically `x_`-prefixed** (`rename`/
  `extension`). Applied: contacts 18 columns, opportunities 45 columns.
- **Merged / app tables**: columns are **`document`ed** as extensions and kept
  as-is (no physical rename).
  - `activities` is a superset of Qobrix **Call | Meeting | Task |
    PropertyViewing | EmailMessage**; its EmailMessage fields (`cc_address`,
    `content_html`, …, `campaign_id`) are therefore **vanilla**, leaving only 3
    genuine app columns — `kind` (row discriminator, values kept Qobrix-aligned:
    `call/meeting/task/property_viewing/email`), `channel`, `touch_outcome` —
    documented as-is. These names are heavily overloaded elsewhere (shortlist
    kind, share channel, …), so a physical rename would carry disproportionate
    blast radius for no vanilla-compliance gain.
  - **App-only tables** that are not Qobrix resources at all (`leads`,
    `collections`, `collection_items`, `collection_shares`, `reservations`,
    `viewing_property_outcomes`, `stage_transitions`,
    `opportunity_field_mismatches`, `opportunity_properties`,
    `contact_relationships`, `sales_entity_notes`, `touch_policies`) are
    documented as whole-table extensions.

Offers and contracts are 100 % vanilla. Zero columns are left unclassified.

**BFF-only response keys.** Edge functions emit presentation/transport keys that
are neither DB columns nor Qobrix fields (`row_source`, `editable`, `tab`,
`column`, `local_opportunity_id`, `owner_name`, `hidden`, and the
`passes/missing/gate` stage-gate verdict). These are app-scoped and never
persisted; the registry documents them so they are not mistaken for drift.

`x_` (not `x_sm_`) is the platform standard already established by
[ADR-023](ADR-023.md); this ADR does not diverge — it applies that rule.

### D3 — No UI words in the data/contract layer

The contract layer never carries display strings. Every user-visible string
resolves through an i18n key in a namespace that mirrors the contract 1:1:

- `qobrix.<resource>.<field>[.<enum>]` — vanilla Qobrix fields/enums,
- `x.<resource>.<field>` — `x_` extensions,
- `app.<feature>.<key>` — app chrome/features with no data counterpart.

Relabeling changes the **word**, never the data. Localizing to any language
(RU first) is data-only: add corpus rows, no code change.

### D4 — The label corpus is app-local, not CDL

This app owns its i18n corpus inside its **own** DB (`rpoeezssicpzexarmwqq`):
`public.app_ui_strings` + `public.ui_terminology`, served by an app-local
`app-i18n` EF and edited by an app-local label-admin EF (both `verify_jwt: false`
with custom SSO-JWT verification per `~/.cursorrules`). English stays bundled as
the first-paint/offline baseline (`src/i18n/locales/en.json`); all other locales
and per-tenant overrides are data (ADR-020/021 pattern, self-contained instead of
CDL-shared). The CDL/RESO corpus is neither moved nor deleted — this app simply
stops reading it.

### D5 — Business-logic math is invariant across the refactor

Naming alignment is identifier-only. Commission, funnel/stage, analytics, and
budget computations keep identical inputs and outputs, verified with before/after
aggregate checks and compatibility views/dual-read during each cutover. The one
true functional regression the audit found — a non-spec `offers.offer_status`
value set introduced during P9c — is reverted to the vanilla enum
`{verbal_offer, written_offer}`; any real lifecycle need is modeled as
`x_offer_lifecycle`, never as a fake Qobrix `status`.

### D6 — Guardrails prevent re-drift

CI fails on: (a) a DB column outside {Qobrix dictionary ∪ `x_*` ∪ infra
allowlist}, (b) new hardcoded JSX strings, (c) an i18n key with no
Qobrix/`x_`/app mapping. `qobrix-dictionary.json` + the extension registry are
living docs referenced by this ADR. Duplicate English *values* across keys are
reported by an **advisory** linter only (`check_i18n_duplicates.mjs`) — see D7.

### D7 — Semantic i18n dedup + vocabulary authority (not textual collapse)

Label deduplication follows industry consensus (Locize / Lokalise /
SimpleLocalize / better-i18n): **textual identity is not semantic identity**.
Identical English strings in different UI contexts MUST keep separate keys when
translations may diverge (homographs, domain context, polite forms). Decision
rule per duplicate value:

1. Different UI context → **KEEP** (declare in `i18n-dedup-allowlist.json`).
2. Same context and Qobrix/`x_` field → **ROUTE** to
   `useUiTerminology().fieldLabel(resource, field)`.
3. Same context and Qobrix enum → **ROUTE** to
   `useUiTerminology().enumLabel(resource, field, code)`.
4. Same-context framework chrome → **MERGE** into `common.*`.

**Vocabulary authority (layered):**

| Layer | Source of display names |
|---|---|
| Qobrix-backed fields/enums | Qobrix API (`docs/document.yaml`) via `ui_terminology` (`qobrix.*` / `qobrixEnum.*`) |
| `x_` extension fields | RESO DD 2.0 Display Names where the `x_` name is RESO-aligned (e.g. Job Title, Lead Source, Contact Type); otherwise humanized `x_`-stripped name |
| Framework chrome | `common.*` / feature namespaces only — never domain nouns |

Machine artifacts in the app repo: `docs/qobrix-vanilla/i18n-dedup-map.json`
(reviewed classification), `docs/qobrix-vanilla/i18n-dedup-allowlist.json`
(intentional homographs), `scripts/check_i18n_duplicates.mjs` (WARN-only,
always exit 0).

### D8 — Source-agnostic runtime terminology (label + definition)

Runtime no longer branches on `qobrix.*` / `x.*` namespaces. Build-time
(`gen_term_definitions.mjs`) resolves **both** label and definition via
**Qobrix → RESO → custom**, tags each with an independent provenance
(`label_source`, `description_source`), and seeds `ui_terminology` with a
**bare** `resource` (`Offer`, `Contact`, `glossary` — no `qobrix.`/`x.` prefix).
`x_` extensions are still identifiable by the field-name prefix.

`app-i18n` serves four content namespaces only:

- `label.<Resource>.<field>` / `labelEnum.<Resource>.<field>.<code>`
- `def.<Resource>.<field>` / `defEnum.<Resource>.<field>.<code>`

Glossary folds in as `label.glossary.<TermId>` / `def.glossary.<TermId>`.
Provenance stays in the DB and is shown only in admin surfaces (term sidebar,
label overrides) — the UI never cares where a default came from.

Runtime edits remain tenant-scoped overrides (`label_source` /
`description_source = 'tenant'`). Every upsert/delete is audited in
`ui_label_history` (who / what / from → to / when) for both corpora.

## Consequences

### Positive
- Internal structure is a faithful, machine-verified projection of the Qobrix
  API — onboarding, sync, and Qobrix round-trips are unambiguous.
- Terminology is fully decoupled from data: any tenant/locale relabel is a data
  edit, never a schema or code change.
- The app is self-contained (no CDL i18n coupling) yet reuses the platform
  ADR-020/021 pattern.
- Semantic dedup keeps locale-safe homographs while collapsing true chrome
  duplicates and centralizing domain labels in the Qobrix/RESO terminology layer.

### Negative / notes
- A one-time, high-touch pass to `x_`-prefix ~80 columns and extract hardcoded
  strings, each behind a compatibility shim so math never breaks.
- Two more EFs and two more tables live in the app DB (accepted for self-containment).
- Divergence from ADR-021's *CDL-hosted* corpus is deliberate and scoped to this
  app (see below).
- Some English strings remain duplicated by design (allowlisted); reviewers must
  not collapse them without checking context.

## KB divergence (per kb-first escape hatch)
- **App-local i18n corpus** in `rpoeezssicpzexarmwqq` instead of the shared CDL
  `app_ui_strings` ([ADR-021](ADR-021.md)). Reason: make this app self-contained
  and free it from platform change-control for its own wording; the CDL corpus is
  left intact and simply unused by this app. The ADR-021 *mechanism* (bundled EN
  baseline + `app-i18n` EF + `app_ui_strings`) is reused unchanged — only the
  hosting project differs. Not a one-off hack: it is the intended pattern for any
  app that must own its terminology independently.
