# ADR-025: Referral + Document as project-flavour CDL resources; offer-economics deferred (zero-`x_`)

**Status**: Accepted
**Date**: 2026-06-08
**Deciders**: Platform team (CDL owners) + Pipeline team
**Related**: [ADR-016](ADR-016.md) (canonical-into-CDL acceleration / `cdl-write`/`cdl-read` dispatchers), [ADR-023](ADR-023.md) (`x_` extension prefix), [ADR-022](ADR-022.md) (`x_contact_key` extension), [cdl-schema.md](../../data-models/cdl-schema.md) ("Week-4: Referral + Document project-flavour resources"), [platform-extensions.md](../../data-models/platform-extensions.md), [matrix-pipeline phases.md](../../product-specs/matrix-pipeline/phases.md) (Week 4), [requirements.md](../../product-specs/matrix-pipeline/wiki/requirements.md) (FR-REF, FR-DOC, FR-TM)

## Context

`matrix-pipeline` 2.0 Week 4 calls for three capabilities: an offer-to-closing
flow on Transactions (FR-TM), Referrals (FR-REF), and Documents (FR-DOC).

A review of the live RESO corpus (`public.reso_field_descriptions` /
`public.reso_lookup_value_descriptions`) established the canonical basis:

- **`TransactionManagement` is a 4-field header only** (`TransactionKey`,
  `TransactionId`, `TransactionType`, `ModificationTimestamp`) — exactly what
  `public.transaction_management` already mirrors. RESO has **no offer-economics
  field and no `Offer` resource**. The canonical close-side fields that *do* exist
  live on the (Atlas-owned, read-only-to-this-app) `Property` resource:
  `Property.ClosePrice`, `Property.PurchaseContractDate`,
  `Property.TransactionBrokerCompensation(Type)`, `Property.StandardStatus`.
- RESO has **no `Referral` resource** (referral is a project-flavour CRM concept).
- RESO has **no `Document` resource** — only Property-level document *flags*
  (`Property.DocumentsAvailable`/`DocumentsCount`/`DocumentsChangeTimestamp`).

Separately, a **scope decision (2026-06-08)** put the entire offer-negotiation
workstream — offer amount/currency, offer/closing dates, terms, the
TransactionManagement↔buyer/property links, the offer lifecycle controls
(Submit/Counter/Accept/Reject/Withdraw/Expire), the FR-TM-07 Property
`Active Under Contract` push, FR-REF-08 automatic referral close-the-loop, and the
forecast P&L block — **beyond scope for now, to be resumed at a later stage**.

## Decision

1. **Defer the offer-economics workstream and keep the datamodel, codebase, and KB
   clean of it.** No `x_` offer columns are added to `public.transaction_management`;
   the existing canonical-minimal Transactions surface (`/transactions` list +
   create + close-edge) is left untouched. The offer lifecycle controls and forecast
   P&L are NOT built this cycle. When the workstream resumes it will use the
   canonical `Property` close-side fields + `Lookup.TransactionType` +
   `HistoryTransactional`, with `x_` reserved only for the genuinely residual
   negotiation gap that has no canonical home.

2. **Model Referral and Document as governed project-flavour CDL resources, not
   `x_` extensions.** `public.referral` and `public.document` are **new resources**
   with no RESO equivalent, so they use plain canonical snake_case columns and
   **carry no `x_` prefix**. The `x_` prefix (ADR-023) marks an extension *of an
   existing RESO resource* (e.g. `x_contact_key` on `ShowingAppointment`); a wholly
   new resource does not take one. They adopt the standard hybrid envelope
   (surrogate `id uuid` PK, `source_id` + `unique(source_id, source_*_key)`,
   `content_hash`, `is_visible`/`is_deleted`/`deleted_at` soft-delete,
   `locked_fields jsonb`, `raw jsonb` GIN, `created_at`/`updated_at` + trigger) and
   are exposed through the existing `cdl-read`/`cdl-write` dispatchers (ADR-016) —
   the app stays a thin client. `document` is **link-only** (`storage_url` →
   external storage; files are NOT stored in the CDL) with a generic
   `related_resource`/`related_key` so it can attach to `Contacts` now and to a
   `TransactionManagement`/offer later without a schema change.

3. **No SSO permission-key layer for these (or any) matrix-pipeline features.**
   `matrix-pipeline` does **not** participate in `sso_app_permissions` (only the
   legacy `agency-portal`/`client-connect`/`meeting-hub` apps do). It authorizes
   pages via **`role_configurations` page keys** (app DB, `useRoleConfig` + admin
   fallback) and gates CDL reads/writes on **SSO JWT scope**
   (`SSO_READ_SCOPES`/`SSO_WRITE_SCOPES`, broker scopes allowed). Therefore the
   Week-4 authorization deliverable is: a `'referrals'` page key seeded into
   `role_configurations`; Documents under the existing `'contacts'` page plus an
   in-app `confidentiality` threshold. **No `pipeline:referrals:*` /
   `pipeline:documents:*` rows are written to SSO** — they would be dead data the
   app never reads.

## KB divergence

- **Plan text "C2 — add SSO permission keys" is intentionally NOT implemented as
  written.** Justification: matrix-pipeline's authorization model is
  `role_configurations` page-keys + CDL JWT-scope, not `sso_app_permissions`
  fine-grained keys; writing those rows would be dead data and would imply a second,
  unused authz path. The *intent* (gate referral/document access by role) is met at
  the page-key + scope layer instead. This is a divergence in implementation layer,
  not in outcome.

## Consequences

### Positive
- The CDL stays 100% canonical: zero non-canonical / speculative `x_` offer columns;
  `TransactionManagement` remains the exact RESO 4-field header.
- Referral and Document ship as first-class, soft-deletable, audited CDL resources
  reusing the existing EF surface — no new EFs, no app-held service-role key.
- `document`'s generic `related_resource`/`related_key` means the later offer
  workstream can attach offer documents to a transaction with no migration.

### Negative / notes
- FR-TM offer flow, FR-REF-08 auto close-the-loop, and forecast P&L are **not
  available** until the deferred workstream is resumed (tracked in `phases.md`).
- Referral `outcome` is **manual** this cycle (Open/Closed Won/Closed Lost) — there
  is no automatic close on deal completion (that needs the deferred TM↔buyer link).
- `referral`/`document` are service-role-only (PII-adjacent / confidentiality), so
  all access is EF-mediated via `cdl-read`/`cdl-write`; there is no direct
  anon/authenticated read path.

## Alternatives considered
- **Add `x_` offer columns to `transaction_management` now** — rejected per the
  2026-06-08 scope decision; keeps the datamodel clean and avoids speculative
  extensions that may not match the eventual canonical `Property` close-side shape.
- **Model Referral/Document as `x_` extensions of an existing resource** — rejected:
  they are not extensions of any RESO resource; they are new resources, so the
  project-flavour-resource pattern (no prefix) is correct (consistent with how
  `saved_search`/`prospecting`/`caravan` were added as canonical resources).
- **Register `pipeline:*` keys in `sso_app_permissions`** — rejected: dead data the
  app never reads (see Decision #3 / KB divergence).
- **Store document files in CDL storage** — rejected: link-only (`storage_url`)
  keeps the CDL free of blob/PII file content and defers a storage/retention policy.
