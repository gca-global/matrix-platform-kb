## [2026-05-26] divergence | role_configurations storage in SSO project

`role_configurations` (CRM role → permission-keys mapping consumed by `ProtectedRoute` and `RoleConfigPanel`) is co-located with SSO permission keys in the SSO project (`xgubaguglsnokjyudgvc`) rather than in the CRM app DB.

Rationale: source of truth for permission keys and role-to-key mappings is the SSO Console, which writes to the SSO project. Mirroring `role_configurations` into the CRM app DB would create a two-source-of-truth problem and require a sync EF for no behavioral gain.

Constraint: CRM app DB **reads** the role configuration via the standard SSO client (`ssoClient` / `ssoAuthedClient`) under the user's SSO JWT. No writes to `role_configurations` from CRM app code.

This is a permitted deviation from `wiki/architecture.md#app-private-state` invariant ("all app-private state lives in CRM app DB only"). The deviation is narrow: it affects exactly one table (`role_configurations`) and its access is read-only.

Tracked in: [wiki/architecture.md#escape-hatch](wiki/architecture.md#escape-hatch) (new "role_configurations co-location" row) + [wiki/architecture.md#app-private-state](wiki/architecture.md#app-private-state) (inline Exception bullet).

Two real defects: **(a)** the `3075065` hook only covered the **direct PostgREST** clients — it never touched `src/lib/edge-functions.ts` `invokeCdl`, which is the path the **Contacts** page uses, so contacts were never going to be fixed by it. **(b)** `isTokenExpired` judges expiry off the **local browser clock** (`Date.now() >= exp − 30s`); when that clock is wrong the client believes a server-expired token is still fresh, and the 401-retry in `invoke()` called `refreshAccessToken()`, which **short-circuits and returns the SAME rejected token** (the "another tab already refreshed" guard), re-sending it forever. A server-minted token always carries server-time `exp`, so it is valid at CDL regardless of the browser clock — meaning the only escape is to actually rotate.

Fix (`a740226`, `matrix-pipeline-2-0`, source-only — `dist` rebuilt by the `github-watcher` auto-deploy): **(1)** new `forceRefreshAccessToken()` in `matrix-sso.ts` — same single-flight + cross-tab Web Lock as `refreshAccessToken`, but bypasses the "still fresh locally" short-circuit and always hits `oauth-token`; wired into the `edge-functions.ts` 401-retry (covers every `invokeCdl`/`invokeSso` call incl. contacts). **(2)** `isTokenExpired` now judges against **estimated server time** (`Date.now() − learnedSkew`); the skew is learned from each issued token's `iat` at `setTokens`, persisted in `matrix_sso_clock_skew_ms`, and is a **no-op for correctly-clocked machines** (<30 s drift) — this fixes the direct PostgREST paths (`role_configurations`, `sso_tenants`, `members`) at the source too. **(3)** follow-up `379835a` makes `scheduleProactiveRefresh` skew-aware too (remaining lifetime computed in server time), so the pre-emptive refresh fires before the server `exp` instead of relying on the reactive 401 round-trip. Verified live: deployed bundle `index-DLf7ogRK.js` on `intranet.sharpsir.group/pipeline` contains the new logic (`matrix_sso_clock_skew_ms`, skew-compensation strings present). No server/EF change. Server-side facts re-confirmed during diagnosis: JWKS publishes exactly one key (`dab1e43f`, ES256) and `oauth-token` signs Pipeline tokens with that same vault key (fails closed otherwise) — so signature/kid was never the cause; this was purely client token-freshness.

## [2026-06-01] fix | Lovable-preview fresh-login loop — bounded authorization-code replay (ADR-019)

Fresh login looped only **inside the Lovable preview** (`invalid_grant` → "the sign-in code expired"); the deployed intranet build logged in fine. Root cause is environmental, not a token bug: the preview rewrites `/auth/callback?code=…` (`callback_lovable_sha` 302s) and loads it across several short-lived documents, **cancelling** the winning `oauth-token` exchange before its response is read. The SSO server enforced **strict single-use** — it consumed the code (`used=true`) but the tokens died with the torn-down fetch, so every later document re-presented the now-spent code and got `400 invalid_grant`; client `waitForSiblingSession` found no published tokens because none were ever stored. A client-only fix is impossible (the fetch context is destroyed). React StrictMode / link-prefetch double-submits are the same failure class.

Fix (server, SSO `xgubaguglsnokjyudgvc`): a **bounded same-client authorization-code replay window** in `oauth-token` (ADR-019). Migration `20260601210000_add_authcode_replay_window` adds `consumed_at` + `issued_access_token` + `issued_refresh_token` to `sso_authorization_codes` (plus `sso_clear_expired_authcode_tokens()` to null cached tokens past the window). The `authorization_code` grant now fetches by `code` alone (dropping `.eq('used', false)`); after **all** existing binding checks (`client_id`, expiry, `redirect_uri`, PKCE) it branches: a **fresh** code mints normally and — **only after a successful mint+persist** (so a signing/storage error no longer burns the code) — records `consumed_at` and caches the issued tokens; a **replayed** code re-presented by the same `client_id`+`redirect_uri` within `REPLAY_WINDOW_MS` (60 s) **re-delivers the identical tokens** (HTTP 200, no new session, no refresh-token rotation), else `invalid_grant`. Redeployed `verify_jwt=false`. **Live-verified**: two immediate POSTs of one synthetic Pipeline code returned byte-identical access + refresh tokens (200/200); the same code aged >60 s → `invalid_grant`; a mismatched client → rejected. No client change required (`AuthCallback.tsx` `waitForSiblingSession` stays a harmless fallback; the loser document's exchange now simply returns 200 and lands home). KB updated same change: [`../../architecture/decisions/ADR-019.md`](../../architecture/decisions/ADR-019.md) (replay-window section + rollout) and [`../../platform/security-model.md`](../../platform/security-model.md) (bounded-replay paragraph). Out of scope (deferred, unverified): dropping `openid` from `redirectToSSOLogin`.
